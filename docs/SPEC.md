## 1. 目的と、この版で変える 1 点

β1.10 は「判断は AI、ツールは配管」という思想で完成している。その配管は正しい。
**問題は入口である。** 使う人はまず「AIで改修する / AIで相談する / 簡易モードで始める」の
3 択を、まだ何も見ていない段階で迫られる。自分のマクロに何が起きているか分からない人には
選べない選択であり、選び間違えると別の道へ入る。

β2.00 が変えるのは 1 点だけである。

> **何をするかは、マクロを見てから決める。**

そのために、読み込んだ直後に**事実監査**を 1 回挟み、その結果を見てから改修内容を決める
一本道にする。分岐は無くなるのではなく、**分岐の位置が「最初」から「診断の後」へ動く**。

### 1.1 中核思想の継続と、1 か所の限定的な修正

β1.10 §1.2「ツールは判断を持たない」は継続する。ただし決定的置換エンジン（§7）のために
**1 か所だけ限定的に修正する**。

| β1.10 §1.2 の記述 | β2 での扱い |
|---|---|
| 「どこが改修対象か・どう直すかの判断はチャット AI がやる。ツールは該当箇所を検出しない」 | **修正**: ツールは VBA の**字句的事実**（文字列リテラルがどこにあり、その値が何か）を検出してよい。ただし「それが誤りである」「こう直すべきだ」は依然として言わない |
| 「返答テキストからモジュール名・コードブロックを抽出する（＝意味の解釈）は禁止」 | **継続**。返答は自分で名乗った区切り行だけを信じる。推定しない |
| 「ひな形は検出ルールでもコード置換規則でもない」 | **継続**。ひな形は依頼の正本であり、置換規則はユーザーが入力する。ひな形は engine を指名するだけ |

区別の要点: **検出（detection）は事実の列挙、判断（judgment）は良し悪しの決定。**
「`"C:\data\"` という文字列リテラルが 3 か所ある」は事実である。
「その固定パスは直すべきだ」は判断であり、ツールは言わない。新しい値を決めるのは常に人である。

## 2. 一本道のフロー

### 2.1 進捗（4 手順）

```
① ブックを読み込む   ② 診断する   ③ 改修を決めて実行する   ④ ブックを作る
```

β1.10 の「用途で進捗バーが変わる」挙動は廃止する。**バーは常に 4 手順で固定**。
最初の画面から 4 段すべてが見えている（要件 E「必須データは最初から表示する」）。

### 2.2 画面表（全 10 画面）

`assets/js/screens.js` が唯一の正本であることは変えない。

| # | 名前 | 手順 | この画面で決めること | ［次へ］が有効になる条件 |
|---|---|---|---|---|
| 0 | `book` | ① | 対象ブック | ブックを読み込めた |
| 1 | `diagnose` | ② | 診断依頼の受け渡しと、診断結果の取り込み | 診断パッケージを受理できた（0 件の結論を含む） |
| 2 | `findings` | ③ | 診断結果を読む（要約・概要・見つかった事実、または採点） | 診断がある |
| 3 | `nextStep` | ③ | 推奨操作（1 つ以上）と変更範囲 | 操作を 1 つ以上選び、変更範囲が決まっている |
| 4 | `repairInput` | ③ | 改修する指摘の確認 | §2.4 の経路別条件 |
| 5 | `repair` | ③ | 改修依頼の受け渡しと、改修返答の取り込み（**AI 経路のみ**） | パッケージを受理できた |
| 6 | `review` | ③ | 変更内容の確認（差分） | 変更が 1 件以上あり、手動修正を開いていない |
| 7 | `output` | ④ | 出力ファイル名 | 名前が正しい（ファイル名のみ・元の拡張子） |
| 8 | `build` | ④ | （自動） | — |
| 9 | `done` | ④ | 出力フォルダを開く / 完了 | （［次へ］の位置は［完了］） |

#### 2.2.0 見える入口はブックだけで、診断は素通りできない

**何をするかは、マクロを見てから決める。** 用途を先に選ばせる画面は持たない。
起動して最初にすることはブックの読み込みで、診断は必ず 1 回通る。何をするかは
診断のあとに「推奨操作」として画面 3 で出す。

一時期、用途を「マクロ改修 / リファクタ / フリー依頼」の 3 入口へ分けて画面 0 に
置いた（[DESIGN-ENTRANCES.md](beta2/DESIGN-ENTRANCES.md)）。それは §1 が
「分岐の位置を最初から診断の後へ動かす」と決めた当のものを最初へ戻す形になっており、
撤回した。経緯と、そのとき解こうとしていた問題を何で解き直したかは
[DESIGN-SINGLE-FLOW.md](beta2/DESIGN-SINGLE-FLOW.md) にある。

`presets/` は入口ごとに分かれず、段階ごとの 3 フォルダーになる。

| フォルダー | 中身 | 数 |
|---|---|---|
| `01_診断/` | 動くかどうかの監査（指摘型） | **ちょうど 1 つ**（0 件・2 件以上は `E-PRESET-02`） |
| `02_改修/` | 推奨操作 | 6 つ |
| `03_変更範囲/` | どこまで変えてよいか | 2 つ（先頭が既定） |

#### 2.2.0.1 推奨操作の見出しはひな形が名乗る（画面 3 前半）

改修ひな形は `## 分類` で、画面 3 のどの見出しの下に立つかを 1 行で名乗る。
同じ行を書いた 2 つのひな形は 1 つの見出しの下に並ぶ。

| 見出し | 中身 |
|---|---|
| 環境依存・外部実行の見直し | Win32 API の互換化／OS・外部プログラムへの依存を減らす |
| 実行環境・参照先の移行 | 固定パスの置換（決定的エンジン）／新しい保存先で成り立つファイル操作 |
| その他の改修 | 診断で見つかった故障を直す／自分で改修内容を書く |

**束ねるのは表示だけである。** 同じ見出しの下の 2 つは別々のひな形ファイルのままで、
別々に選べ、選んだものだけがそれぞれ `【ひな形名】` 付きで改修依頼へ入り、
run manifest にも別項目として残る。アプリは渡された文字列で束ねるだけで、
見出しの一覧を持たない（`tests/test-shortest-path.js` がアプリ内に分類名が
書かれていないことを検査する）。

`## 分類` を持たない改修ひな形は `E-PRESET-01` で、画面にその理由が出る。
立つ場所の無いカードを黙って消さないためである。

#### 2.2.0.2 変更範囲（画面 3 後半）

**リファクタは用途ではなく、どこまで変えてよいかである。** 画面 3 の下段で選ぶ。
既定は先頭のファイルで、詳細オプションを開くと残りが出る。

| 選択肢 | `## 構造変更` | 既定 |
|---|---|---|
| 必要最小限の変更 | `禁止` | ● |
| 大規模な構造変更・リファクタリングを許可する | `許可` | |

どちらの名前も**許すことで**書く。「〜しない」を外す形の選択肢は置かない。

選んだファイルの `## 改修指示` は `{{CHANGE_SCOPE}}` として改修依頼の【変更範囲】へ
そのまま入る。文面はファイルにしかなく、アプリは複製しない。

`禁止` のあいだ、取り込みは文面に頼らず**次の 4 つを機械的に検査する**（§5.4）。
使える変更範囲が 1 つも無いビルドでは、既定を勝手に決めず画面がそう言い、
先へ進まない。

**見つかった事実は、判定 → 問題 → 該当箇所の 3 段で見せる。** 同じ環境キーを
名指しした指摘は 1 つの問題である。Sleep を 11 か所で呼ぶマクロは、決めることが 1 つ
で、見る場所が 11 か所なので、そのとおりに出す。上部の件数は**問題の数**であって
該当箇所の数ではなく、該当箇所の数は括弧で添える。既定で開いているのは判定と
問題までで、該当箇所とその根拠は読者が開いたときだけ出す。改修する指摘の選択も
同じ判定順で、チェックは問題単位に入り、その問題に属する該当箇所すべてを取り込む。

#### 2.2.1 A〜D（当初の判定を置き換えた）

この版で当初やっていた判定（要改修 / 要確認 / 改修不要）は、**このツールがその
環境キーのひな形をたまたま持っているか**で決まっていた。それはアプリが意味を
決めていたということで、言えることも「うちにそのファイルがあるかどうか」に
限られていた。これを AI の採点へ移す。指摘 1 件ごとに、入口の基準に照らして A〜D が付いて返ってくる。

`01_マクロ改修` の A〜D は「動くかどうか」だけで決まる。裁量の余地は無い。

| 等級 | 意味 | 画面の言い方 |
|---|---|---|
| A | 動作に支障なし | 動作に支障はありません。読むだけで結構です |
| B | 要改修（動かない／このツールで直せる） | 動きません。このツールのひな形で改修を依頼できます |
| C | 不明（動かない／原因がコードの外にある） | 動きません。環境の側で手を打つことになります |
| D | 改修不可（動かない／置き換え先が無いことが確定） | このマクロをこの環境で動かすことはできません |

D は「何もできない」という最も重い言い方なので、`CONFIDENCE=CONFIRMED` でなければ
受理しない（`D11`）。確信が持てないなら C である。

**依頼に入るのは B だけである。** C は原因がコードの外にあり、D は置き換え先が無い。
どちらも依頼に入れれば「できないこと」を頼むことになる。画面 4 は B だけを並べ、
C と D が何件あってどこへ行くか（完了画面の引渡しメモ）をその場で言う。

採点型の診断（`## 返す形` が `採点型`）はブック全体に 1 つだけ等級を付ける。その
基準は、使える改修ひな形がちょうど 1 つのときのその `## 改修指示` であり、依頼文には
`{{GRADING_BASIS}}` として**その 1 ファイルから**差し込む。仕様書にも診断ひな形にも
書かない。同じ基準が 2 か所にあれば必ずずれるからである。同梱の診断は「動くか」を
問う指摘型なので基準を要さず、この変数は空のまま消える。

上部の帯は 4 つの等級を**常に 4 つとも**出す。「要改修 0」は「この分類には何も無い」
という事実ではなく「あなたがこのツールでやることは無い」という答えなので、0 でも出す。

★推奨は**別の問いのまま**である。等級は「動くか」、★は「そのひな形がこの環境キーを
扱うと名乗っているか」。等級が★を付けることはない。

**指摘の該当行はコードで見せる。** `LINES` が指す行を強調したモジュールを、
置換画面と同じ表示部品（`assets/js/code-view.js`）で開く。既定は該当箇所のみで、
前へ／次へで該当箇所を渡り歩ける。組み立ては**開かれたときだけ**行う。

**診断は素通りできない。** 直したいことが決まっている読者は、画面 4 の
「追加の要望」欄（`## 記入欄` を宣言したひな形ならその名前の欄）に書けばよく、
そのために診断を飛ばす経路を作らない。診断を飛ばせる道は、名前が何であれ
「診断する / しない」というトップレベルの分岐であり、§1 が動かした分岐の位置を
最初へ戻してしまう。

**診断結果には 2 つの形がある。** 診断ひな形が `## 返す形` で宣言する。
`指摘型`（findings）は指摘の列を返し、`採点型`（grade）はブック全体に 1 つの等級と
その理由を返す。返す節も `## 返す節` でひな形が決める（監査は PURPOSE / FLOW /
DEPENDENCY / ENVIRONMENT、採点は PURPOSE / FLOW / DEPENDENCY / REASON）。
一方の形で頼んで他方の形が返ってきたら、空の結果として読まずに拒否する
（`D02` / `D12` / `D20` / `D26`）。採点の結果画面は「これは AI の見立てです」と
明示する。事実ではなく判断だからである。

**診断を読むことと、次にすることを選ぶことは別の決定である。** 前者は事実の理解、
後者は作業の選択で、同じ画面に置くと読み終える前に選択肢が目に入る。診断ページの
上部には診断全体を 2〜3 行で述べる要約を既定表示し、マクロの概要（何をするもので、
どう動いていて、何に頼っていて、対象環境で何が起きるか）と各指摘の根拠は、同じ形の
行から開く。ひな形の並び順は `02_改修/` の先頭番号で決まり、見出しの並び順は
その順で最初に現れた `## 分類` の順である。ひな形は
`## 推奨条件` に書いた環境キーを、受理済み診断の指摘が名指ししているときだけ
「★ 推奨」を表示する。根拠のない推奨は作らない。

**依頼の受け渡しと返答の取り込みは 1 画面である。** チャットへ渡して答えを持ち帰る
のはひとつのまとまった作業で、間に［次へ］を置く理由がない。分けていたときは、
取り込み画面にボタンが 1 つしか無い空の画面が生まれ、［次へ］を押す回数だけが
増えていた。渡す操作は画面を進める条件ではなく、**答えが返ってきたことだけが
進める条件**である。旧 `diagnoseRequest` / `diagnoseIntake` は `diagnose` に、
旧 `repairRequest` / `repairIntake` は `repair` に統合した。`screens.js` は旧名も
同じ番号へ解決する別名として公開し続ける。

**画面 0 は β1.10 の画面 1 と 2 の統合である。** 読み取り結果（モジュール名と行数、
`read.level` の伝え方）は同じ画面の折りたたみへ入れる。β1.10 §5.1.2 の 2 段階の
伝え分け（コードに疑いがある / 管理情報だけ）はそのまま維持する。

**消える画面**: β1.10 の画面 0（作業を選ぶ）と画面 2（読み取り結果の専用画面）、
および一時期あった入口の画面。
**消える入口**: 「AIで相談する」「簡易モードで始める」「マクロ改修 / リファクタ /
フリー依頼」。用途を先に名乗らせる画面は、名前が何であれ置かない。

### 2.3 分岐は 1 か所だけ

`nextIndex` が持つ分岐は 1 つに限る。それは**選んだひな形が持っているものだけ**から
決まり、飛ばした画面はそもそも載せるものが無い画面である。

1. **画面 4 → 5 / 4 → 6**: 選んだひな形のどれかが AI へ渡す文
   （`## 改修指示` と `## 出力指示`）を持つなら 5 へ、`## 置換の候補` だけを
   持つひな形しか選ばれていなければ 6（確認）へ。**この分岐はユーザーに見えない。**
   `## 置換の候補` を持つひな形を AI 経路のひな形と一緒に選んだ場合、
   画面 4 が 2 段になる。**先に置換を実行し**、同じ画面が続けて
   「AI に何を直してもらうか」を聞き、その置換済みコードを AI へ渡す（§7.2）。
   画面は増えず、順序も変わらない。

質問（`## 質問`）は画面を増やさない。選んだひな形が質問を持てば画面 4 の上部に
質問欄が加わるだけである（β1.10 の質問専用画面は廃止した）。

### 2.4 画面 4 の［次へ］条件（経路別）

条件は**すべての項を満たす**（`AND`）。「または」で緩めない。

| engine | 条件 |
|---|---|
| `AI` | (1) 選んだひな形の `## 質問` があるなら**全問に回答済み** **かつ** (2) 選んだ指摘が 1 件以上 **または** 自由記述欄（`## 記入欄` を宣言したひな形ならその欄、それ以外は「追加の要望」）が非空 |
| `対応表による置換` | (1) `applied` のマッピング行が 1 行以上 **かつ** (2) `applied` の**全行**が §7.6 の検証に合格 |
| 両方（置換がまだ） | 上の `対応表による置換` の条件。置換が済むと同じ画面が `AI` の条件に切り替わる |

**前進のボタン文言はどの画面でも［次へ］である。** 画面ごとに名前を変えると、
読者はその画面だけ別のボタンを探すことになる。

**選んだ指摘そのものが指示である。** 指摘は何が・どこで・何を壊すかを
すでに述べているので、指摘ごとの再記述は求めない
（β2.00 実装で希望動作の入力欄・候補チップ・「維持すること」の常時表示は
画面から外した。ひな形の `## 希望動作の候補` と `## 維持すること` は
依頼文の側に残る）。

置換のボタンを押すと、その場で置換を計算して画面 6（確認）へ進む。
**別ウィンドウ・別モーダル・進捗ダイアログは出さない。**

### 2.5 戻る

［戻る］は実際に通った経路を逆にたどる（β1.10 と同じ history stack）。
画面 8（build）中だけは戻れない。画面 0（ブック）からは戻る先が無い。

診断をやり直したいときは画面 1 へ戻って取り込み直す。ブックを読み込み直すと
診断以降の全状態を捨てる（取り込み済みがあれば確認ダイアログ）。
**変更範囲を選び直すと、書き済みの改修依頼は古くなる。** 依頼はその答えを本文に
持ち、取り込みはその答えを機械的に検査するからである。診断は捨てない。「動くか」の
答えはどこまで変えてよいかで変わらない。ブックも捨てない。変更範囲が既定へ戻るのは
別のブックを読んだときだけである。

#### 2.5.1 完了画面（画面 9）から戻る

**戻れる。そして戻っても実行は完了したままである。**

完了画面に着いた時点で、改修済みブック・差分 HTML・`result.md` は**すでにディスク上にある**。
誤って進んでしまった人や、確認画面をもう一度読みたい人を閉じ込めないため
［戻る］は塞がない。一方で、戻った先が**何も起きなかった画面に見えてはいけない**。

したがって:

- `buildResult` と `buildTimestamp` を **［戻る］では消さない**。
  消してよいのは出力を実際に無効化する操作だけ（対応表の変更、取り込みのやり直し、
  次のビルドの開始）。
- 戻った先の各画面（画面 8・9 を除く）に「**この実行は完了しています／
  作成済みのファイルはそのまま残っています／このまま進めると同じフォルダーへ
  もう一度作成します**」を出し、出力フォルダーのパスを添える。

戻って続きの改修 → 再ビルドができる（§13.11）のは従来どおりで、
2 世代目は前世代を退避してから置き換える（§9.4）。

### 2.6 状態の帰属（β1.10 の不変条件を 2 段階へ拡張）

依頼 ID だけに紐づけると、**ID が同じまま前提が変わった**ときに古い結果が生き残る。
そこで各段階の成果物は、自分が答えた**前提一式のスナップショット**に帰属させる。

| 成果物 | 帰属する前提 |
|---|---|
| 診断パッケージ | ブックの内容署名 ＋ **環境定義の正準スナップショット** ＋ 診断依頼 ID |
| 改修パッケージ / 決定的置換の結果 | 診断結果の版 ＋ 選んだひな形の**ファイル名と内容** ＋ 全入力（質問の回答・選択した指摘・希望動作・追加の要望・マッピング） ＋ 改修依頼 ID |

- **環境定義の正準スナップショット**: `target-environment.json` の内容を
  §3.6 の整形へ通した結果の文字列。画面 1 へ入るたびファイルを読み直すため、
  読み直した結果がスナップショットと違えば「依頼を作り直す」条件になる（§4.2.1）。
  ファイルを編集して版が上がったのに古い依頼で診断を受け取る、という状態を作らない。
- **診断結果の版**: 診断を受理するたびに 1 つ増える整数。同じ診断依頼 ID へ
  取り込み直した場合でも版が変わるので、それに基づく改修入力と改修結果は無効になる。

無効化の規則（左が起きたら右を捨てる）:

| 起きたこと | 捨てるもの |
|---|---|
| ブックを読み込み直した | すべて（実行フォルダごと新しい実行） |
| 変更範囲を選び直した | 改修依頼から下流すべて（診断とブックは残す） |
| 環境定義が変わった状態で画面 1 へ入った | 診断依頼から下流すべて |
| 「ほかに気になっていること」を変えて［依頼を作り直す］ | 同上 |
| 分割受理のチェックを切り替えた | 同上（受け取り済みの part も含む） |
| 診断を取り込み直した（版が上がった） | 選択・希望動作・追加の要望・改修依頼・改修パッケージ・決定的置換の結果・差分 |
| ひな形を選び直した（ファイル名または内容が変わった） | 質問の回答・選択・希望動作・追加の要望・マッピング・改修依頼から下流 |
| 画面 4 の入力を変えた（回答・選択・希望動作・追加の要望・マッピング） | 改修依頼・改修パッケージ・決定的置換の結果・差分・出力名 |
| 不成立の回答（`NOCHANGE <判断>`）を受理した | 改修パッケージ（判断と理由は画面 5 に残る。§5.4.1） |

- 診断結果が無い状態で画面 3 以降へ入ることはできない。
- **ひな形は選んだ時点の内容をスナップショットする。** 画面 3 へ入るたび
  `presets/` を読み直すため、外部でファイルが変わっていれば内容が変わる。
  変わっていたら上表の「ひな形を選び直した」と同じ扱いにする。

#### 2.6.1 状態の確定はホストの成功後（transaction）

新しい依頼 ID・スナップショット・状態を、**ファイル書き出しが成功する前に確定しない**。

1. 画面 4 →5（または 1 への初回入場）で、入力のスナップショットを取る。
2. ホストへ書き出しを依頼する。この間、前進ボタンは `disabled`（二重押下を作らない）。
3. **ホストが成功を返してから**、新しい ID・スナップショット・下流の破棄を一度に確定する。
4. ホストが失敗を返したら、**ファイルも状態も 1 か所も変わっていない**。
   古い依頼 ID・古いファイル・古い結果がそのまま残る。

ホスト側の書き出しも同じ規律に従う。`diagnose-request.md` の世代交換・
`repair-request.md`・`diagnosis.md` は **一時ファイルへ書く → flush / close →
本来の名前へ置き換える**（β1.10 §5.4 の再ビルドの世代交換と同じ方式）。
途中で失敗しても前の世代が壊れない。

## 3. 想定動作環境（実データ）

### 3.1 ファイル

```
macrostudio/
└── environment/
    ├── target-environment.json   … 機械可読の正本（アプリが実行時に読む）
    └── SOURCES.md               … 出典・版管理・改訂履歴（人が読む・保守する）
```

**コード内に同じ内容を持たない。** C# にも JS にも fallback の既定値を置かない。
ファイルが無い・壊れている場合はアプリが止まる（§3.5）。

### 3.2 スキーマ（`schemaVersion: 1`）

```json
{
  "schemaVersion": 1,
  "profileId": "new-business-terminal",
  "displayName": "新しい業務端末",
  "revision": "2026-08-01",
  "summary": "EDR / DLP 管理下の Windows 端末。ブックは SharePoint / OneDrive 上に置かれる。",
  "sources": [
    { "id": "ms-preset-04", "origin": "macrostudio", "path": "presets/04_新しい端末で動くかを調べてもらう.md", "readAt": "2026-08-01" }
  ],
  "constraints": [
    {
      "key": "WIN32API_BLOCKED",
      "axis": "execution",
      "effect": "blocked",
      "title": "Win32 API の Declare 呼び出しが実行できない",
      "detail": "宣言だけでなく、その API を呼んでいる箇所も動かない。",
      "basis": "declared",
      "sourceIds": ["ms-preset-04", "devkit-analyze-edr"],
      "examples": ["Declare", "Declare PtrSafe"]
    }
  ]
}
```

| フィールド | 必須 | 規則 |
|---|---|---|
| `schemaVersion` | ○ | 整数。`1` 以外は**未知として拒否**（推測で読まない） |
| `profileId` | ○ | `/^[a-z][a-z0-9-]{2,63}$/` |
| `displayName` | ○ | 非空。画面に常時出る |
| `revision` | ○ | 非空。画面に常時出る |
| `summary` | ○ | 非空。1〜3 行 |
| `sources[]` | ○ | 1 件以上。`id` は非空かつ一意。`origin` / `path` / `readAt` 必須 |
| `constraints[]` | ○ | 1 件以上 |
| `constraints[].key` | ○ | `/^[A-Z][A-Z0-9_]{2,39}$/`。全体で一意。**診断契約の `ENVKEY` が参照する** |
| `constraints[].axis` | ○ | `execution` / `storage` / `host` / `components` / `office` / `platform` |
| `constraints[].effect` | ○ | `blocked`（動かない） / `changed`（動くが結果が変わる） / `uncertain`（確認が必要） |
| `constraints[].title` | ○ | 非空。1 行 |
| `constraints[].detail` | ○ | 非空 |
| `constraints[].basis` | ○ | `observed`（実測した） / `declared`（前提として宣言した） / `inferred`（設計上そうなるはず） |
| `constraints[].sourceIds` | ○ | 1 件以上。すべて `sources[].id` に存在すること |
| `constraints[].examples` | — | 文字列配列。**プロンプトへ渡す例示専用**。コードの走査には一切使わない |

### 3.3 同梱する内容の出典

初期値は次の 3 つの実物から抽出する（[AUDIT-BETA1.md](beta2/AUDIT-BETA1.md) §2）。

| sourceId | 出典 | 与えるもの |
|---|---|---|
| `ms-preset-04` | `macrostudio/presets/04_新しい端末で動くかを調べてもらう.md` | 5 つの前提（Win32 API / 外部プロセス / パスの URL 化 / 端末依存の固定値 / 古い部品） |
| `devkit-analyze-edr` `devkit-analyze-compat` `devkit-analyze-path` | `pub/vba-devkit/config/analyze.json` と `lib/Analyze.ps1` | 3 軸 38 項目の列挙と、`observed` / `inference` の別 |
| `datadesk-envtest` | `pub/datadesk/envtest/modules/*.ps1` | 環境事実集合の軸の語彙（runtime / office / webview / security / network / exe / communication）と `ok/missing/error` の記録規律 |

**`basis` の初期値はすべて `declared` または `inferred` である。**
`observed` を名乗る項目は初期状態では 0 件でよい。理由:
`datadesk/envtest/results/` は `.gitignore` されており実測結果が存在せず、
README が参照する `.repos/CONSTRAINTS.md` も存在しないため
（[AUDIT-BETA1.md](beta2/AUDIT-BETA1.md) §2.2.1）、**測っていないものを測ったと書かない**。

`vba-devkit` の `Basis = 'observed'` は「その検出パターンが検証で実際に立った」という
意味であって「対象端末でその制約が実測された」ではない。混同せずに `inferred` へ落とす。

### 3.4 読み込み

- 新 IPC action `getTargetEnvironment` → `{content}`（`environment/target-environment.json`
  を strict UTF-8 で毎回読み直す）。**ホストは中身を解釈しない**（§1.2 の継続）。
- 検証と解釈は `assets/js/target-environment.js` **だけ**が持つ。第 2 実装を作らない。
- 読み直す契機: 起動時と、画面 2（診断依頼）へ入るたび。ファイルを編集しても再起動不要。

### 3.5 fail-fast

次のいずれかで **E-ENV-01** とし、画面 2 にカードを出して**診断へ進めない**。
トーストで流さない。既定値へ落ちない。

- ファイルが無い / 読めない / strict UTF-8 として不正 / JSON として不正
- `schemaVersion` が `1` でない
- §3.2 の必須フィールド欠落・型不一致・列挙外の値
- `constraints[].key` の重複、または命名規則違反
- `sourceIds` に `sources[].id` へ存在しない id がある
- `constraints` が 0 件

カードには「何が起きたか」と「どのファイルを直せばよいか」を書く。
`environment\target-environment.json` の相対パスは出す（絶対パスは出さない）。

#### 3.5.1 失敗の内部 ID（利用者へは出さない）

**利用者が見るコードは `E-ENV-01` の 1 つだけ**である。これは変えない。
ただし検証の失敗には**内部 ID** を持たせ、`EnvironmentError` に
`validationId` として載せる。

| validationId | 条件 |
|---|---|
| `ENV-READ` | ファイルが無い / 読めない / strict UTF-8 として不正 |
| `ENV-JSON` | JSON として不正 |
| `ENV-SCHEMA` | `schemaVersion` が `1` でない |
| `ENV-FIELD` | 必須フィールドの欠落・型不一致 |
| `ENV-ENUM` | `axis` / `effect` / `basis` が列挙外 |
| `ENV-KEY` | `constraints[].key` の命名規則違反 |
| `ENV-KEYDUP` | `constraints[].key` の重複 |
| `ENV-SOURCE` | `sourceIds` が空、または `sources[].id` に存在しない |
| `ENV-SOURCEDUP` | `sources[].id` の重複 |
| `ENV-EMPTY` | `constraints` が 0 件 |

**なぜ要るか**: この節は 10 個の異なる条件を 1 つの利用者向けコードへ畳んでいる。
内部 ID が無いと、否定テストは「`E-ENV-01` で落ちた」としか言えず、
**意図した条件とは別の条件で落ちていても気づけない**
（例: 「key 重複」の fixture が、実は必須欄の書き損じで `ENV-FIELD` に落ちていても
テストは通る）。これは codex-implementer が C6 で指摘した
「負例が正しい理由で落ちたことを検査する」と同じ問題である。

各否定 fixture は**自分の `validationId` を名指しで assert する**
（[PLAN-BETA2.md](beta2/PLAN-BETA2.md) §4.1-2）。

### 3.6 プロンプトへの組み込み

診断テンプレート `templates/diagnose-template.txt` の変数 `{{TARGET_ENVIRONMENT}}` へ、
次の固定形式で差し込む（ASCII 罫線。全体をバイト単位で回帰テスト固定する）。

```
================================================================================
 TARGET ENVIRONMENT: 新しい業務端末 (new-business-terminal / rev 2026-08-01)
================================================================================
EDR / DLP 管理下の Windows 端末。ブックは SharePoint / OneDrive 上に置かれる。

[WIN32API_BLOCKED] execution / blocked / declared
  Win32 API の Declare 呼び出しが実行できない
  宣言だけでなく、その API を呼んでいる箇所も動かない。
  例: Declare, Declare PtrSafe

[SHELL_EXEC_BLOCKED] execution / blocked / declared
  外部プログラムの起動が実行できない
  Shell 関数、WScript.Shell、cmd /c による外部プロセスの起動が止められる。
  例: Shell, WScript.Shell, cmd /c
--------------------------------------------------------------------------------
 basis: observed=実測 / declared=前提として宣言 / inferred=設計上の推定
================================================================================
```

- 並び順は `axis` の定義順（`execution` → `storage` → `host` → `components` →
  `office` → `platform`）、同一 axis 内は `key` の昇順。**入力ファイルの並びに依存しない。**
- `examples` が無い項目は「例:」行を出さない。
- この整形は `target-environment.js` の `renderForPrompt()` だけが持つ。

## 4. 第 1 段階: AI 診断（事実監査）

### 4.1 この段階が決めること・決めないこと

| 決める | 決めない |
|---|---|
| マクロの目的 | 改修方針 |
| 処理の流れ | 改修後の動作予測 |
| 依存関係 | 「改修不要」の結論 |
| 対象環境で動くか（阻害要因の列挙） | どのモジュールをどう書き換えるか |

契約は**構造でこれを強制する**。診断パッケージには**直し方を書く欄が存在しない**。
文章で「直し方を書かないでください」と頼むだけにせず、書く場所を与えない。

例外として「この監査範囲では動作阻害要因を確認できなかった」は結論として認める（§4.6）。

### 4.2 依頼の作り方

画面 2 へ**初めて入った時点**で:

1. 診断依頼 ID（UUID v4）を発行する。
2. 実行フォルダを作る（§8.1）。
3. `source-code.md` を書き出す（β1.10 §6.2 の固定形式のまま。全モジュール・省略なし）。
4. `templates/diagnose-template.txt` を strict UTF-8 で読み、変数を差し込んで
   `diagnose-request.md` を書き出す。
5. `01_診断/` の唯一の有効ファイルから `## 改修指示` と `## 出力指示` を取る。
   `02_改修/` に有効なひな形が 1 つだけなら、その `## 改修指示` を
   `{{GRADING_BASIS}}` として差し込む（§2.2.1）。複数あるなら差し込まない。
   （診断の依頼文も `{{REQUEST_TEXT}}` になるため、見出し名は `## 改修指示` のまま使う。
   理由は [DECISIONS-BETA2.md](beta2/DECISIONS-BETA2.md) D-13）

#### 4.2.1 依頼を作り直す条件（1 実行 = 1 フォルダを守る）

上の 1〜4 は**画面 2 へ入るたびには起きない**。［戻る］で画面 1 へ出て入り直しても、
同じ依頼 ID・同じフォルダ・同じファイルを使い続ける。作り直すのは次の 2 つだけである。

| 契機 | 起きること |
|---|---|
| ブックを読み込み直した | 新しい実行。ID・フォルダ・全ファイルを作り直し、診断以降の状態を捨てる（取り込み済みがあれば確認ダイアログ） |
| 画面 2 で「ほかに気になっていること」を変えて［依頼を作り直す］を押した | 新しい診断依頼 ID を発行し、同じ実行フォルダの `diagnose-request.md` を**世代交換で置き換える**（β1.10 §5.4 の再ビルドと同じ規則）。診断結果・選択・希望動作・改修パッケージを捨てる |

分割受理のチェックを切り替えた場合も、出力指示が変わるため
［依頼を作り直す］と同じ扱いにする（受け取り済みの part も捨てる。§4.7）。

差し込み変数（β1.10 §6.3 の表に追加）:

| 変数 | 必須 | 値 |
|---|---|---|
| `{{REQUEST_TEXT}}` | ○ | 診断ひな形の `## 改修指示` ＋ 利用者の「ほかに気になっていること」 |
| `{{TARGET_ENVIRONMENT}}` | ○ | §3.6 の整形済みブロック |
| `{{OUTPUT_RULES}}` | — | 診断ひな形の `## 出力指示` |
| `{{REQUEST_ID}}` `{{BOOK_NAME}}` `{{MODULE_COUNT}}` `{{TOTAL_LINE_COUNT}}` `{{MODULE_LIST}}` `{{CODE_FILE_NAME}}` | — | β1.10 と同じ |

`{{TARGET_ENVIRONMENT}}` が診断テンプレートに 1 回以上無ければ **E-GEN-02**。
未知変数・壊れた変数表記も従来どおり E-GEN-02（fallback しない）。

### 4.3 診断ひな形

`presets/01_診断/` に**ちょうど 1 つの有効なファイル**を置く。同梱は
`presets/01_診断/01_動くかどうかの監査.md`（指摘型）1 つだけである。
採点型（`## 返す形` が `採点型`）を宣言できる機構は残るが、同梱の診断は使わない。

- 0 件または 2 件以上の有効ファイル → **E-PRESET-02** で画面 1 を止める。
  黙って先頭を選ばない（β1.10 簡易モードの「並び順で最初のもの」方式は踏襲しない）。
- 診断は選ぶものではないので、この一覧を画面に出さない。ひな形名も出さない。

### 4.4 診断パッケージ形式

区切り行の語彙・字句規則は β1.10 §6.5 と**完全に共通**にする。
行全体が区切りである場合だけ区切りとして扱う（前後の空白は無視）。先頭は `'`。
依頼 ID が一致しない `'@MACROSTUDIO` 行が 1 つでもあれば**全体を拒否**する。

```
'@MACROSTUDIO <ID> DIAG BEGIN 1
'@MACROSTUDIO <ID> SECTION BEGIN PURPOSE
（このマクロが何をするためのものか）
'@MACROSTUDIO <ID> SECTION END PURPOSE
'@MACROSTUDIO <ID> SECTION BEGIN FLOW
（処理の流れ）
'@MACROSTUDIO <ID> SECTION END FLOW
'@MACROSTUDIO <ID> SECTION BEGIN DEPENDENCY
（依存関係。参照ライブラリ・外部ブック・シート・名前定義・外部プログラム）
'@MACROSTUDIO <ID> SECTION END DEPENDENCY
'@MACROSTUDIO <ID> SECTION BEGIN ENVIRONMENT
（対象環境で動くかの総括）
'@MACROSTUDIO <ID> SECTION END ENVIRONMENT
'@MACROSTUDIO <ID> FINDING BEGIN 1
'@MACROSTUDIO <ID> META GRADE=B CONFIDENCE=CONFIRMED MODULE=CommonUtil PROC=WaitSeconds LINES=12,13 ENVKEY=WIN32API_BLOCKED
'@MACROSTUDIO <ID> TEXT BEGIN TITLE
（1 行。何が起きるか）
'@MACROSTUDIO <ID> TEXT END TITLE
'@MACROSTUDIO <ID> TEXT BEGIN CONDITION
（成立条件。どういうときにそうなるか）
'@MACROSTUDIO <ID> TEXT END CONDITION
'@MACROSTUDIO <ID> TEXT BEGIN IMPACT
（影響。何が起きるか・データはどうなるか）
'@MACROSTUDIO <ID> TEXT END IMPACT
'@MACROSTUDIO <ID> TEXT BEGIN EVIDENCE
（根拠。コードのどこを見てそう言えるか）
'@MACROSTUDIO <ID> TEXT END EVIDENCE
'@MACROSTUDIO <ID> FINDING END 1
'@MACROSTUDIO <ID> DIAG COMPLETE 1
'@MACROSTUDIO <ID> DIAG END
```

#### 4.4.0 短い書き方（2026-08-03 追加）

上の形は、指摘 1 件あたり区切り 11 行になる。区切り 1 行につき 36 文字の
依頼 ID が乗るので、**本文より区切りのほうが長くなる**。読む側の負担である
と同時に、AI が書き間違える機会がその数だけあるということでもある。

そこで、同じ内容を次の形でも受理する。指摘 1 件が区切り 1 行と本文 4 行になる。

```
'@MACROSTUDIO <ID> DIAG BEGIN 1
'@MACROSTUDIO <ID> SECTION PURPOSE （このマクロが何をするためのものか。1 物理行）
'@MACROSTUDIO <ID> SECTION FLOW （処理の流れ）
'@MACROSTUDIO <ID> SECTION DEPENDENCY （依存関係）
'@MACROSTUDIO <ID> SECTION ENVIRONMENT （対象環境で動くかの総括）
'@MACROSTUDIO <ID> FINDING 1 GRADE=B CONFIDENCE=CONFIRMED MODULE=CommonUtil PROC=WaitSeconds LINES=12,13 ENVKEY=WIN32API_BLOCKED
TITLE: （1 行。何が起きるか）
CONDITION: （成立条件）
IMPACT: （影響）
EVIDENCE: （根拠）
'@MACROSTUDIO <ID> DIAG COMPLETE 1
'@MACROSTUDIO <ID> DIAG END
```

- `SECTION <名前>` の本文はその行の残り。次の区切りまでの行も本文に足す
  （Markdown が改行を畳んだ返答を組み直した場合、本文は次の行に来るため）。
- `FINDING <番号>` の残りは META と同じ 6 つの `key=value` で、順序も同じ。
  §4.4.1 以降の検査は、どちらの形でも**同一の関数**が行う。
- `TITLE:` / `CONDITION:` / `IMPACT:` / `EVIDENCE:` は区切りではなく本文行の
  先頭タグ。全角コロンも受ける。次のタグまでが本文。
- 2 つの形は 1 つの返答の中で混ざってよい。1 つの指摘の中では混ざらない。
- 同梱ひな形の記入例は短い形で書く。長い形は引き続き受理する
  （既に手元にある返答を捨てさせないため）。

#### 4.4.0.1 チャットが付けた装飾を落とす

返答が取り込めないことは、この道具で最も頻繁に起きる不満である。原因の多くは
AI の間違いではなく、チャットの画面が返答を飾ったことにある。次の装飾は
**パース前に機械的に外す**。外した結果が区切り行になる場合だけ採用し、
そうでなければ元の行をそのまま使う（本文は決して書き換えない）。

- Markdown のフェンス行（言語名の有無を問わず）
- 引用の `>`（全行が引用ならまとめて 1 段外す）
- 箇条書き・番号付きの行頭記号
- 行を囲むバッククォート、`<code>` `<pre>` `<span>` などのタグ
- HTML エスケープ（`&#39;` `&quot;` `&lt;` `&gt;` `&amp;` `&nbsp;`）
- 行頭の曲がったアポストロフィ・全角 `＇`・全角 `＠`、および落ちた `'`

これは受理範囲を広げるだけで、依頼 ID の照合（D01）、途中切れ（D02）、
件数（D19/D29）などの検査は一切緩めない。

#### 4.4.1 META 行

1 行 1 指摘のメタ情報。**キーの順序・個数を固定**し、`key=value` を半角空白 1 つで区切る。
値に空白は入らない（入る値は TEXT ブロックへ置く）。欠落は `-` と書く。

| キー | 値 | 規則 |
|---|---|---|
| `GRADE` | `A` / `B` / `C` / `D` | 必須。列挙外は拒否。意味は診断ひな形が決める（§2.2.1） |
| `CONFIDENCE` | `CONFIRMED` / `LIKELY` / `UNVERIFIED` | 必須。列挙外は拒否 |
| `MODULE` | モジュール名 または `-` | `-` 以外は**添付したブックに実在する名前**（case-insensitive 照合）。実在しなければ拒否 |
| `PROC` | プロシージャ名 または `-` | VBA 識別子として妥当。**実在は照合しない**（プロシージャの列挙を持たないため。名乗りを事実として扱わず、画面では「AI が指した名前」として出す） |
| `LINES` | `12` / `12,13` / `12-20` / `-` | 正準 10 進・カンマ・ハイフンのみ。範囲は開始 ≤ 終了。**1 起点で、画面に出しているコード（先頭 Attribute ブロック除去後）の行番号**。`MODULE` の行数を超える値は拒否 |
| `ENVKEY` | 環境定義の `key` または `-` | `-` 以外は**読み込んだ環境定義に実在する key**。実在しなければ拒否 |

**該当箇所の整合規則**（要件 B「該当モジュール/プロシージャ/行を持たせる」を、
名乗るだけで通らないようにする）:

| 規則 | 検査 ID | 断る理由 |
|---|---|---|
| `PROC` が `-` でないなら `MODULE` も `-` でない | D23 | どのモジュールの話か分からないままプロシージャ名だけを名乗っている |
| `LINES` が `-` でないなら `MODULE` も `-` でない | D24 | どのモジュールの話か分からないまま行番号だけを名乗っている |
| `LINES` の全ての行番号が 1 以上かつ `MODULE` の可視行数以下 | D25 | 存在しない行を指している |

**なぜ 2 つに分けているか**（実装時に codex-implementer が指摘した点の記録）:
当初この規則は「`MODULE=-` なら `PROC` と `LINES` も `-`」と
「`PROC` か `LINES` が `-` でないなら `MODULE` も `-` でない」の 2 本だったが、
この 2 つは**対偶であり論理的に同値**である。したがって片方だけを破る入力は作れず、
「各検査に落ちる fixture を 1 件ずつ」の規律の下で一方の ID が到達不能になる。
**強制する不変条件は変えないまま**、offender となるフィールドで分割した。
`MODULE` だけを名乗り `PROC` / `LINES` が `-` の指摘は**正常**である
（モジュール単位までしか特定できていない、という事実の表明）。

**`GRADE` と `CONFIDENCE` の整合規則**: `GRADE=D` の指摘は
`CONFIDENCE=CONFIRMED` でなければならない（D11）。D は「このマクロをこの環境で
動かすことはできない」という最も重い言い方であり、推量で言えることではない。
確信が持てないなら C である。

**`ENVKEY` の扱いは緩めた。** 当初は `CLASS=BLOCKER` に環境キーを必須にし、
その制約の `effect` が `blocked` であることまで求めていた。しかし環境に由来しない
単純な故障（コンパイルエラー、明らかに不合理な動作）も「動かない」であり、
それを B と言えないのは分類の側の欠陥だった。いまは `ENVKEY=-` の指摘にも
どの等級も付けられる。環境キーを名乗った場合にそれが環境定義に実在することは
引き続き求める（D14）。

#### 4.4.2 `CONFIDENCE` と `basis` は別のものである

混同しやすいので明示する。**この 2 つは別の主体の、別の対象への確からしさである。**

| | 誰の | 何に対する |
|---|---|---|
| `CONFIDENCE`（`META` の値） | **AI の** | **コードを読んだ結果**の確からしさ（この箇所が本当にそうなっているか） |
| `basis`（環境定義の値） | **私たちの** | **環境の前提**の確からしさ（対象端末で本当にそうなるか） |

したがって `CONFIDENCE=CONFIRMED` の指摘が `basis=inferred` の制約を指すことは
**矛盾ではない**。「コードにこの API 呼び出しが確かにある（CONFIRMED）。
その API が対象端末で止まるという前提は推定である（inferred）」という状態を表す。

画面はこの 2 つを**別のチップとして並べて出す**（§6.2）。片方だけを見せない。
環境キーを名乗り、その `basis` が `observed` でない指摘には、
第二層に「この環境前提は実測ではありません」の 1 行を添える。

B に `CONFIDENCE=LIKELY` を許すのも同じ理由による。
`GRADE` は**その指摘が読者に何を求めるか**を表し、
`CONFIDENCE` は**その読み取りの確からしさ**を表す。
「直せる故障である可能性が高い」は意味のある状態であり、拒否しない。
D だけは例外で、確信を要求する（上記）。

#### 4.4.3 等級と表示順

画面の表示順は**重いものから**に固定する。読者が最初に見るのは、いちばん重い
等級が何を求めているかである。

| 順 | GRADE | 意味（`01_マクロ改修`） | 画面 |
|---|---|---|---|
| 1 | `D` | 改修不可（確定） | 常時展開 |
| 2 | `C` | 不明（原因がコードの外） | 常時展開 |
| 3 | `B` | 要改修（このツールで直せる） | 常時展開 |
| 4 | `A` | 動作に支障なし | 常時展開 |

A も畳まない。β2 の `INFO` は「主結果ではないもの」だったが、A は
「この指摘については何もしなくてよい」という**結論**であり、隠す理由がない。

#### 4.4.4 採点型（`## 返す形: 採点型`）

診断ひな形が採点型を宣言した場合、返答は指摘を持たず、代わりに
`'@MACROSTUDIO <ID> DIAG GRADE <A-D>` を**ちょうど 1 行**持つ。
`DIAG BEGIN` と `DIAG COMPLETE` はどちらも `0`、`FINDING` と
`DIAG NOFINDING` は書かない。返す節はひな形の `## 返す節` が決める
（`02_リファクタ` は PURPOSE / FLOW / DEPENDENCY / REASON）。

形が食い違う返答は、空の結果として読まずに拒否する。

| 起きたこと | 検査 ID |
|---|---|
| 採点型に指摘が入っている | D26 |
| 採点型に `DIAG NOFINDING` が入っている | D20 |
| 採点型に `DIAG GRADE` が無い／等級が列挙外 | D12 |
| 指摘型に `DIAG GRADE` が入っている | D02 |

**`DIAG BEGIN` の数字は書式の版ではなく件数である。** β2.00 の実測でこう変えた。
版だったころ、その数字が何なのかをひな形は一言も書いておらず、この書式で行末に
数字が付く他の区切り（`FINDING BEGIN <番号>` / `DIAG COMPLETE <件数>` /
`PART <n> OF <n>`）は**すべて番号か件数**だった。結果、4 件の正しい診断が
`DIAG BEGIN 4` で始まり、D03 で全体が拒否された（2026-08-02、`S01_fixed_drive`）。
書式が教えているとおりに読んだ答えを拒否する契約は、契約の側が誤っている。

版は wire から外した。返答は MacroStudio が発行した依頼 ID に束縛されており、
その ID を持つ依頼はこの版の依頼文しか作らないので、別の版の返答が紛れ込む経路が無い。
数字を件数にしたことで、上端と下端の 2 か所が中身と突き合わされるようになり、
検査は 1 本増えている（D29）。

失敗時は **E-DIAG-01**。画面には例外文・記号・検査番号を出さず、
次にどうすればよいかを 1 文だけ伝える。ログには検査番号（D01 等）を残す。

#### 4.5.1 数の読み方（`COMPLETE` と `PART` は別規則）

β1.10 は `COMPLETE` の数を `Number()` で変換して比較していたため、
`1.0` / `0x2` / `1e0` / `Infinity` を module 数と一致すれば受理していた
（[AUDIT-BETA1.md](beta2/AUDIT-BETA1.md) §1.4.1 A1）。
`/^\d+$/` を課すだけでは `01` が通るため、**それだけでは足りない**。

| 用途 | 規則 |
|---|---|
| `COMPLETE <n>` / `DIAG COMPLETE <n>` | **正準 10 進表記**: `/^(0\|[1-9][0-9]*)$/`。そのうえで `String(実際の件数) === <n>` の**文字列一致**で判定する。数値変換を一切経由しない。`01` / `1.0` / `0x2` / `1e0` / `+1` / 全角数字はすべて拒否 |
| `PART <番号> OF <合計>` | **β1.10 の既存挙動を変えない**。`/^\d+$/` の 0 起点整数として読み、`00` 表記を受理する。同じ part を `0` と `00` の両方で名乗ることは、正準化した値が一致するため**同一 index として扱う**（内容が同一なら冪等、異なれば conflict） |

区切り行そのものの読み方（前後の空白を無視し、語を空白で分割する）は β1.10 のまま変えない。
**したがって語の間の空白の数は検査対象にしない。** 検査するのは語の並びと各語の形である。

`FINDING <n>` / `DECISION <n>` の番号も正準 10 進表記とし、
`1` と `01` が同じパッケージに同居することを**拒否**する（D07 / §5.4.1）。
表示と並べ替えは正準化した数値で行い、パッケージ内の記載順には依存しない。

### 4.6 指摘が 0 件のとき

```
'@MACROSTUDIO <ID> DIAG BEGIN 1
（SECTION 4 種は必須。省略できない）
'@MACROSTUDIO <ID> DIAG NOFINDING SCOPE_CLEAR
'@MACROSTUDIO <ID> DIAG COMPLETE 0
'@MACROSTUDIO <ID> DIAG END
```

| `<理由>` | 意味 | 画面の伝え方 |
|---|---|---|
| `SCOPE_CLEAR` | この監査範囲では動作阻害要因を確認できなかった | 「この監査範囲では動作阻害要因を確認できませんでした。」 |
| `INSUFFICIENT` | 判断に必要な情報が足りない | 「判断に必要な情報が足りませんでした。」＋ ENVIRONMENT 節の本文を続けて出す |

- 4 つの SECTION は 0 件でも必須である。**指摘が無いことと、読んでいないことは違う。**
- `SCOPE_CLEAR` は「問題が無い」ではない。文言でも「確認できませんでした」と書き、
  「問題ありません」「改修不要です」とは書かない（§4.1）。
- 0 件でも画面 3 へ進める。ひな形（固定パス置換や自由記述）は選べる。
  一本道を 0 件で行き止まりにしない。

### 4.7 長い診断の分割受理

β1.10 §6.6 と**同じ機構・同じ語**を使う。`DIAG BEGIN` の直後に 1 行足すだけ。

```
'@MACROSTUDIO <ID> DIAG BEGIN 1
'@MACROSTUDIO <ID> PART 00 OF 03
```

**統合はテキストの連結ではない。** 各 part は自分の `DIAG BEGIN` / `DIAG END` /
`DIAG COMPLETE` を持つので、本文をそのまま繋ぐと統合後に `DIAG BEGIN` が
複数現れて D02 / D18 に違反する。**構造体として統合する。**

処理は 2 相に分ける。どの検査をどちらで行うかを次の表で固定する。

| 相 | 何をするか |
|---|---|
| **相 1 `parsePart`** | 1 つの返答を単独で解析し、その中で閉じている検査だけを行う |
| **相 2 `mergeParts`** | 全 part がそろった時点で構造体を統合し、全体でしか判定できない検査を行う |

| 検査 | 相 1（part ごと） | 相 2（統合後） |
|---|---|---|
| D01 依頼 ID | ○ | — |
| D02 `DIAG BEGIN`/`END` 対応 | ○（その part の中で） | — |
| D03 `DIAG BEGIN` の件数の形 | ○ | — |
| D04 `SECTION` 4 種が揃う | **part 00 のみ**。01 以降は SECTION が 1 つでもあれば拒否 | ○（統合後に 4 種が揃っていること） |
| D05 `SECTION` 種別 | ○ | — |
| D06〜D17, D23〜D28 各 `FINDING` の内部 | ○ | — |
| D07 `FINDING` 番号の一意性 | ○（part 内） | ○（**全体**で一意。別 part の同番号は拒否） |
| D18/D19 `DIAG COMPLETE` | ○（**その part に含まれる件数**と一致） | — |
| D29 `DIAG BEGIN` の件数 | ○（**その part に含まれる件数**と一致） | — |
| D20/D21 `NOFINDING` | — | ○（**全体 0 件のときのみ**。§4.7.1） |
| D22 外側に sentinel が無い | ○ | — |
| `PART` の整合 | ○（1 本だけ・`/^\d+$/` の 10 進数字列・`0 ≤ 番号 < 合計`・`合計 ≥ 1`。**`00` 表記を受理する**。§4.5.1 の `PART` 規則） | ○（全 part で `<合計>` 一致・欠番なし） |

- `<番号>` は 0 起点、`<合計>` は 1 以上（読み方は §4.5.1 の `PART` 規則）。
- `DIAG COMPLETE <n>` は**その返答に含まれる指摘の件数**（β1.10 の `COMPLETE 1` と同じ考え方）。
  統合後の総件数を名乗る行は**存在しない**。総数の担保は `PART ... OF <合計>` が行う。
- 同じ番号の再送は、正規化後の本文が**完全に同一のときだけ**冪等に受け入れる。
  内容が違えば拒否し、集めた分は変えない。
- 欠番のまま先へ進めない。何番が足りないかを画面が名指しする。
- 全部そろったら番号順に統合する。**統合後の構造体は、同じ内容を一度で受け取った場合と
  完全に同一**でなければならない（要件 A「下流では同じ内部形式へ統合する」）。
  これをテストで固定する。
- **相 1 で通った検査を相 2 でもう一度回さない。** 二重拒否も取りこぼしも作らないよう、
  上の表が唯一の割り当てである。
- 分割を使うかどうかは画面 1 の折りたたみ内のチェック 1 つで選ぶ。ON にすると
  診断ひな形の `## 出力指示（分割）` が出力指示に入れ替わる。切り替えると
  それまでに受け取った part を捨てる（2 つの返し方を混ぜない。§4.2.1）。

#### 4.7.1 分割時の 0 件

`NOFINDING` は**全体で 0 件のときにだけ**成立する。したがって分割形式では
`PART 0 OF 1`（＝ part が 1 つしかない）のときにのみ許す。

- `PART 0 OF 3` で `DIAG COMPLETE 0` かつ `NOFINDING` は**拒否**する
  （残り 2 つに指摘があるかもしれない状態で「指摘なし」を名乗っている）。
- 途中の part が `DIAG COMPLETE 0` で `NOFINDING` を持たないことは**正常**である
  （その返答には指摘が入っていなかっただけ）。
- 全 part がそろって総件数が 0 なのに、どの part も `NOFINDING` を持たない場合は
  D20 で拒否する（無言の 0 件）。

### 4.8 受理後の成果物

診断を受理した時点で、実行フォルダへ `diagnosis.md` を書き出す。
人が読める整形（見出し＋箇条書き）で、META の値と 4 つの TEXT をそのまま載せる。
これは記録であり、以降の処理はこのファイルを読まない（正本はメモリ上の内部形式）。

### 5.4 画面 5 — 改修返答の取り込み

|---|---|---|
| R1 | `COMPLETE <n>` の `<n>` を**正準 10 進表記＋文字列一致**で判定する（§4.5.1）。`PART` は既存挙動のまま | β1.10 は `Number()` 変換のため `1.0` / `0x2` / `1e0` を受理していた。`/^\d+$/` だけでは `01` が通るため足りない（[AUDIT-BETA1.md](beta2/AUDIT-BETA1.md) §1.4.1 A1） |

#### 5.4.1 返せる答えは 2 つだけ

改修段階で AI に許す最終回答は次の 2 つで、3 つ目は無い。

| # | 形 | 中身 |
|---|---|---|
| 1 | 成功 | 指定形式で、改修後の完全なコードを返す |
| 2 | 不成立 | `NOCHANGE <判断>` と、そう判断した理由を `SUMMARY` に返す |

`<判断>` は 3 つ。

| 値 | 意味 |
|---|---|
| `UNNECESSARY` | いまのままで依頼の内容を満たしている |
| `IMPOSSIBLE` | 直したほうがよいが、渡されたモジュールを書き換える形ではできない |
| `UNCLEAR` | 依頼の内容が、渡された情報だけでは確定できない |

**利用者へ逆質問する回答、選択肢を示して選ばせる回答は禁止する。**
コードを返す形式の中に質問を混ぜる回答も同じく禁止で、
`DECISION` / `TEXT BEGIN QUESTION` / `TEXT BEGIN OPTIONS` の区切りを 1 つでも
含む返答は **R3（`questionNotAllowed`）で拒否**する。
追加情報がなければ決められない場合も対話を始めず、`UNCLEAR` と理由で返す。

理由は次のとおりである。この製品の受け渡しはクリップボードと添付ファイルの
一往復であり、対話を続ける経路を持たない。質問を受け取っても、利用者は
それを画面のどこかへ書き写して、依頼文を作り直して渡し直すしかない。
それは「依頼を書き直す」という同じ操作を、遠回りに見せているだけである。
決められない理由が読めれば、利用者は依頼文を直してもう一度渡せる。

不成立の回答は画面 5 に留まり、判断と理由を表示してビルドへは進まない。
［最初から取り込み直す］で別の返答を取り込み直せる。
（β2.00 初期の `NEEDDECISION` と `DECISION` ブロック、
差し戻し質問を画面 4 へ引用する仕組みは 2026-08-02 に撤去した。）

#### 5.4.2 変更範囲の検査（`## 構造変更` が `禁止` のとき）

選んだ変更範囲が `禁止` を名乗っているあいだ、取り込みは**依頼文の言い回しに
頼らず**、返答そのものを検査する。契約（§4.5 / β1.10 §6.5）を通ったあと、
モジュールが 1 つも取り込まれる前に走り、1 つでも当たれば**返答全体を拒否**する。
一部だけ適用した状態は作らない。

| # | 検査 | 拒否の理由（`reason`） |
|---|---|---|
| 1 | 読み込んだブックに無いモジュール名が返答に含まれる | `structureNewModule` |
| 2 | 既存モジュールの返答から、元にあった `Sub` / `Function` / `Property` の宣言が消えている | `structureRemovedProcedure` |
| 3 | 別の既存モジュールにあった手続き名が、このモジュールの返答に現れている（そのモジュールの元コードに無かったもの） | `structureMovedProcedure` |
| 4 | 元が 40 行以上のモジュールで、変更行数（追加＋削除）が元の行数の 80% 以上 | `structureRewritten` |

拒否の文は**何を見つけたか**を名指しする（増えたモジュール名、消えた手続き名、
移動元のモジュール名、行数）。「構造が変わっています」だけでは、読者に確かめる
場所が残らない。文には選んでいる変更範囲の名前も入れ、詳細オプションで許可すれば
進めることを言う。

**手続きとして数えないもの**が 2 つある。

- `Declare` 文。VBA の文法上は `Function` だが、これを取り除くことは
  Win32 API 改修そのものである。手続きの削除として数えると、この製品が最もよく
  行う改修が既定設定で通らなくなる。
- そのモジュールの元コードに既にあった名前（検査 3）。VBA は `Test` や `Main` を
  複数のモジュールに私的に持てるので、名前だけで突き合わせると、動いていない
  手続きが「移動した」と出る。

**検査 1 の例外は、選んだ操作が自分で名乗る。** 改修ひな形が
`## 認める構造変更` に `- モジュール追加` と書いていれば、その操作を選んでいる
あいだモジュールの追加を通す。Win32 API の代替関数を新しい標準モジュールへ
まとめる改修は、その操作自体が要求している構造変更であって、黙って混ぜ込まれた
ものではない。**どの操作がそれを名乗るかをアプリは知らない。**

**検査していないことを、検査したとは言わない。** ここに挙げた 4 つ以外の構造変更
（手続きの中身の作り替え、変数の整理、コメントの書き直し）は検出できない。
画面 3 は 4 つを列挙したうえで、その限界を同じ場所に書く。

なお**新しいクラスモジュール・ユーザーフォームの追加は変更範囲に関係なく常に
拒否**される（`newModuleKind`、β1.10 からの契約）。既存モジュールの種別の
食い違いはブック側の種別へ矯正される。したがって「クラス化」は変更範囲以前に
通らない。ここに新しい検査は足さない。

## 6. UI 仕様

### 6.1 原則

1. **一つの中央作業面。** 最大幅 880px の 1 カラム。左右にペインを持たない
   （β1.10 の確認画面のモジュール一覧＋diff の 2 ペインだけは例外として維持する）。
2. **必須データは最初から表示する。** 対象ブック名、想定環境の名前と版、

3. **任意データは入口が明確で、既定は畳む。** ラベルは中身を名乗る
   （「詳細設定」「オプション」は禁止）。**その場で開く。**
   別設定画面・別モーダル・別トップ動線へ追い出さない。
4. **主結果が先、証拠は淡い第二層。** 第二層は `--text-sub` / 12〜13px /
   左 3px のレール付きブロックで、地の色は変えない。
5. **入れ子は 1 段まで。** 開閉領域の中に開閉領域を置かない。
   例外は指摘一覧の 1 か所だけとし、`INFO` グループ（1 段目）の中の各指摘（2 段目）に限る。
6. 警告と、操作がまだできない理由は、開閉領域へ入れない。

### 6.2 分類と確度の視覚語彙

β1.10 の状態辞書（青=作業中 / 緑=完了 / 灰=未処理 / 赤=削除・失敗）を壊さない。
診断の分類には**別の軸**を割り当て、既存の色に意味を足さない。

| GRADE | チップ | 色トークン |
|---|---|---|
| `D` | `D` `改修不可` | `--danger` 塗り・白字 |
| `C` | `C` `不明` | `--danger-text` 文字・`--danger-soft` 地 |
| `B` | `B` `要改修` | `--accent-text` 文字・`--accent-soft` 地 |
| `A` | `A` `支障なし` | `--text-sub` 文字・`--surface-hover` 地 |

等級の名前（`改修不可` など）はアプリが持つ。これはアプリ自身の読み方であり、
ひな形の言い分ではない（`tests/test-no-domain-knowledge.js` が守らせている）。

| CONFIDENCE | チップ |
|---|---|
| `CONFIRMED` | `確認済み` |
| `LIKELY` | `可能性高` |
| `UNVERIFIED` | `未確認` |

確度チップは常に分類チップの右、`--type-micro`、輪郭のみ。塗らない。

### 6.4 狭い画面・長い内容

**縦スクロールの器はちょうど 1 つである。**

- トップバー・進捗バー・画面見出し・フッターの操作領域は**固定**。
- その間の**画面本文（`.screen-body`）が唯一の縦スクロール器**（`overflow-y: auto`）。
  `body` は決してスクロールしない。
- 「指摘一覧だけがスクロールする」方式は**採らない**。画面 4 が最長になる状態
  （質問全件 ＋ 選択した指摘ごとの希望動作欄 ＋ 追加の要望 ＋ 維持すること、
  あるいはマッピング行が数十行）では、一覧だけを縮めても他が収まらない。
- 画面 3 は、画面本文の中で**指摘一覧に残りの高さを配る**
  （結論帯と概要 4 行と ひな形カードを引いた残り）。一覧が短ければ器も短くなる。
- **フォーカス移動時のスクロール**: キーボードで画面本文の外にある要素へ移ったとき、
  ブラウザ既定の `scrollIntoView` に任せず、`.screen-body` の中だけをスクロールさせる。
  固定領域がずれないことをテストで確認する。
- 幅 1100px 未満で、指摘行の第二層が 2 列（該当箇所 / 根拠）から 1 列へ落ちる。
- 幅 1024px 未満で、結論帯の件数チップが 2 行へ折り返す。
- 長い行（パス・診断本文・コード）は**それぞれの領域内で横スクロール**する。
  `body` は横スクロールしない。
- 指摘が 0 件のときも一覧の枠は出し、「この監査範囲では動作阻害要因を確認できませんでした。」
  を中に置く（空の枠を消して画面を作り替えない）。

## 7. 決定的置換エンジン（固定パスの置き換え）

### 7.1 ユーザーから見えるもの

**見えるのはひな形 1 枚だけである。**
画面 3 のひな形カードに `固定パスを新環境へ置き換える` が並ぶ。他のひな形と同じ形・
同じ大きさ・同じ位置。「モード」「エンジン」「決定的」という語を画面に出さない。
別ウィンドウ・別入口・エンジンの選択肢を出さない。

段階の骨格は AI 改修と同じである。
*ひな形を選ぶ → 対象と希望を入力する → 実行する → 差分を確認する → コピーを出力する。*
違うのは、画面 4 の中身がマッピング表であることと、実行が手元で終わることだけである。

### 7.2 dispatch

経路を決めるのは**ひな形が何を持っているか**であって、名乗った engine 名ではない。
ひな形は複数選べるので、1 回の実行が両方の仕事を持つことがある。

| 選んだひな形が持つもの | 経路 | 画面 |
|---|---|---|
| `## 改修指示` と `## 出力指示` だけ | AI 経路 | 4 条件 → 5 受け渡し・取り込み → 6 差分 |
| `## 置換の候補` だけ | 決定的置換経路 | 4 対応表・実行 → 6 差分 |
| 両方（1 枚でも、2 枚を選んでも） | 両方 | 4 対応表・実行 → 同じ 4 で条件 → 5 → 6 差分 |

**両方の経路は、機械的置換を先に行う。** 置換予定の行を含んだコードを AI へ渡すと、
返ってきたコードに古い値が残る。だから画面 4 は 2 段になり、先に対応表を実行し、
**その結果のコードを AI へ渡す**。依頼文には「この値は置き換え済みで、元へ戻さない」
という約束を書く（`machineReplacementNote`）。画面の順序は変わらない。

読み取ったブックのコードは最後まで動かない。画面 6 の差分は経路によらず
**原本 → 最終形**であり、`exports/source-code.md` は常に原本である。
置換済みコードになるのは `temp/source-code-for-ai.md` だけである。

機械的置換が済んだ事実は `state.appliedMapping` が持ち、後から来る AI の返答で
消えない。AI の返答・`改修できません`・取り込みのやり直しは**返答を捨てるだけ**で、
置換結果のコードは復元される（`restoreReplacedModules`）。返答が触れなかった
モジュールが原本へ戻ってしまうと、最終ブックに古い値が残るためである。
`result.md` は置換の対応表と AI の要約を両方載せる。

`preset-document.js` が解釈し、`screens.js` の `nextIndex` が画面 4 → 5 / 4 → 6 を選ぶ。
`## 置換の候補` の行が読めなければ **E-PRESET-01**（ひな形の書式不正）。

**何を候補として拾うかはひな形が決める。** `## 置換の候補` は
`- 呼び方 | 正規表現 | 既定で選ぶ | 場所を選ぶ | 拾わない文脈 | 拾う文脈` の
箇条書きで、`path-map.js` は `detect(modules, rules)` にこれを渡されて
当てはめるだけであり、パスが何かを知らない（§7.4）。3 つ目以降は省ける。

規則が言えることは 3 つ増えている。**どれも省いたひな形は以前と同じに読まれる。**

| 書き方 | 意味 |
|---|---|
| 正規表現の**捕獲グループ**（丸かっこ） | 置き換えの単位を**リテラルの一部**にする。書かなければリテラル全体で、これが従来の挙動 |
| 5 つ目の欄 **`拾わない文脈`** | リテラルの**直前にあるコード**に当てる正規表現。当たった行はその候補を名乗らず、下の行に順番が回る |
| 6 つ目の欄 **`拾う文脈`** | 同じく直前のコードに当てる正規表現。書いた場合、**当たらない限りその候補を名乗らない** |

`拾う文脈` は `拾わない文脈` の鏡である。字面だけでは何とも言えないが、
使われ方で決まるものがある。プリンタ名は任意の文字列であり、
`Application.ActivePrinter = ` の右にあるという事実だけがそれをプリンタ名にする。
これを `拾わない文脈` で書こうとすると「それ以外のすべての文脈」を
列挙することになり、書けない。

捕獲グループを持つ規則が当たったとき、対応表の行は**捕獲された部分**で束ねられる。
同じフォルダーが複数の接続文字列に現れても行は 1 つで、置換時は
各出現が自分の前後（`prefix` / `suffix`）を持ち回り、リテラルを組み直す。
置換直前の再確認は**リテラル全体**の一致を見る（一部だけを置き換える場合も同じ）。
一致しなければ **E-MAP-02** で何も置き換えない。

この 2 つが要る理由は、リテラル単体を見る正規表現では原理的に届かない場所があるためである。
`"WScript.Shell"`（ProgID）と `"Report.Backup"`（本物のファイル名）は**字面が同型**で、
分けているのは前者が `CreateObject(` の中にいるという**文脈**のほうである。
接続文字列は 1 リテラルだが、**場所はその中の一部分**であり、全体を単位にすると
`Extended Properties="Excel 12.0 Xml;HDR=YES"` まで人が打ち直すことになる。

決定的置換だけのひな形は `## 改修指示` と `## 出力指示` を持たなくてよい
（AI へ渡さないため）。`# 名前` と `## 説明` と `## 置換の候補` があればよい。
`preset-document.js` はこの条件分けを持つ。

### 7.3 字句解析（`assets/js/vba-lexer.js`）

**正規表現で行を眺める方式は採らない。** `pub/vba-devkit` の
`(?mi)^[^''\r\n]*"[A-Z]:\\"` 方式は、文字列中のアポストロフィ（`"Don't"`）で誤爆し、
`REM` コメントを避けられず、行継続で分断されたパス連結を追えない
（[AUDIT-BETA1.md](beta2/AUDIT-BETA1.md) §2.1）。**書き換えるツールにこの精度は足りない。**

物理行ごとに 1 文字ずつ走査し、次の 3 種のトークンへ分ける。

| kind | 規則 |
|---|---|
| `string` | `code` 状態の `"` で開始。`""` は文字列中のダブルクォート 1 個。単独の `"` で終了。**物理行をまたがない** |
| `comment` | `code` 状態の `'` から行末まで。加えて、**文の先頭**の `REM` に続く空白または行末から行末まで（大小無視） |
| `bracket` | `code` 状態の `[` から対応する `]` まで（VBA の外部識別子・`Evaluate` 短縮形）。**この中では `'` も `"` も特別扱いしない** |
| `code` | それ以外 |

補足規則（いずれも実装とテストの対象）:

- **「文の先頭」の定義**: 次のいずれかの直後（空白は読み飛ばす）。
  1. 物理行の先頭
  2. `code` 状態の `:`（文区切り）の直後。ラベル行 `Label1:` の後もこれに当たる
  3. **物理行の先頭の空白に続く数字行ラベルの直後**（`100 Rem "C:\secret"`）。
     VBA は行番号ラベルを許すため、これを文の先頭として扱わないと
     `100 Rem` の後ろの文字列を候補にしてしまう。
     判定は `/^[ \t]*\d+[ \t]+/` に一致する部分の直後（`100 GoTo 200` も同じ形）。
     式の中の数字（`x = 100 + 1`）は行頭ではないのでこれに当たらない。

  `REMark` のような識別子はコメントにならない
  （`REM` の直後が空白か行末のときだけコメント）。
- **日付リテラル `#2026-08-01#`**: `code` として扱ってよい。中に `"` も `'` も現れないため、
  文字列・コメントの判定を乱さない。特別な状態を持たない。
- **条件付きコンパイル `#If` / `#ElseIf` / `#Else` / `#End If` / `#Const`**:
  字句としては通常の `code`。ただし入れ子の深さを数え、
  `#If ... Then` 〜 `#End If` の**内側にある出現**には印を付け、
  §7.5 の根拠表示に「条件付きコンパイルの内側」と出す（コンパイルされない可能性を
  利用者へ伝えるため。置換の可否は変えない）。
  - `#ElseIf` / `#Else` は深さを変えない。`#If` で +1、`#End If` で −1。
  - **釣り合っていない場合**（`#End If` が多い、または `#If` が閉じないままモジュールが終わる）は、
    そのモジュールの**全出現を `ambiguous` にして鍵を掛ける**（安全側）。
    深さを推測して続行しない。
- 文字列が閉じないまま行末に達した場合、その行を `unterminatedString` として印を付け、
  その行の候補はすべて `ambiguous` にする（VBA としても構文エラーであり、触らない）。
  同様に `]` が閉じないまま行末に達した行も `unterminatedBracket` として同じ扱いにする。
- **論理行**: `code` 状態で、行末が空白 + `_` で終わる物理行は次の物理行へ続く。
  文字列中・コメント中・`bracket` 中の `_` は継続ではない。
  論理行は「根拠の表示」と「連結されたパスの検出」に使う。
  置換は常に**物理行の中のトークン位置**に対して行う。
- **可逆性**: トークン列を順に連結すると元の物理行が
  **UTF-16 文字列として完全一致で**復元できること（§7.3.1）。
  これをテストで固定する（`test-vba-lexer.js`）。字句解析が壊れていれば、
  置換より先にこの検査が落ちる。

### 7.3.1 座標系（曖昧さを残さないための定義）

| 概念 | 定義 |
|---|---|
| 対象テキスト | モジュールの**可視コード**（先頭 Attribute ブロック除去後）。β1.10 §8 と同じく改行は CRLF に正規化済み |
| `line` | **1 起点**の物理行番号 |
| `column` | **0 起点**の、その物理行内の **UTF-16 コードユニット**オフセット |
| 行の分割・再結合 | CRLF で分割し、CRLF で結合する。末尾の CRLF の有無は入力のまま保つ |
| 「元と同じ」の意味 | **UTF-16 文字列としての完全一致**。「1 バイトも違わない」という言い方は、
デコード後の JS 文字列に対しては不正確なので使わない |

サロゲートペア（絵文字・一部の漢字）を含む行でも `column` はコードユニット数で数える。
`test-vba-lexer.js` の可逆性検査に、CRLF / LF のみ / 末尾改行なし / 日本語 /
サロゲートペアを前置した行の fixture を必ず入れる。

### 7.4 候補の検出

**`string` トークンだけを見る。`comment` / `code` / `bracket` は候補にしない。**
変数名・プロシージャ名・コメント・外部識別子は決して置換対象にならない。

まず「そもそも候補か」を決める。**次の述語が偽なら、その文字列は候補にならない**
（`ambiguous` にもならない。一覧に出さない）。

```
isPathish(value) =
     value に "\" が含まれる
  || value に "/" が含まれる
  || /%[A-Za-z_][A-Za-z0-9_()]*%/ に一致する部分がある
  || /\.[A-Za-z0-9]{1,8}$/ に一致する（末尾がファイル拡張子の形）
```

候補になった文字列に、**出現ごとに**次の順で class を与える。
最初に当たったものを採る。正規表現はコードブロックで示す（表内で `|` を書くと
markdown の列区切りと衝突するため）。

```
P-DRIVE-01  driveAbsolute  /^[A-Za-z]:[\\/]/
P-UNC-01    unc            /^\\\\[^\\]/
P-URL-01    url            /^(?:https?|ftp):\/\//i
P-ENV-01    envVar         /%[A-Za-z_][A-Za-z0-9_()]*%/
P-KNOWN-01  knownFolder    大小無視で "\Users\" "\Desktop" "\Documents"
                           "\AppData" "\Program Files" のいずれかを含む
P-FRAG-01   fragment       "\" か "/" を含み、同じ論理行で "&" により連結されている
P-BARE-01   bareName       区切り文字を含まず、同じ論理行に
                           Workbooks.Open / Dir / SaveAs / Open(For) /
                           FileSystemObject / GetObject のいずれかがある
P-AMB-01    ambiguous      isPathish だが上のどれにも当たらない
P-AMB-02    ambiguous      unterminatedString / unterminatedBracket の行にある
                           （この規則は他のすべてに優先する）
```

| class | 既定の扱い |
|---|---|
| `driveAbsolute` `unc` `url` `envVar` | 入力欄が開いた状態で提示 |
| `knownFolder` `fragment` `bareName` `ambiguous` | **要確認**（既定は鍵付き。§7.6） |

**`envVar` の範囲を絞った理由**: 「同じ論理行に `Environ` がある」を条件にすると、
`Environ("APPDATA")` の `"APPDATA"`（環境変数の**名前**であってパスではない）まで
候補になる。判定は**その文字列自身が `%NAME%` を含むか**だけにする。

### 7.5 集約と根拠の表示

- **集約の鍵は「値そのもの」だけである**（`groupKey = 値`）。class は鍵に入れない。
  同じ値が文脈によって別の class に分類されうるため、`class:値` を鍵にすると
  「同一値ごとに 1 行」が破れる。
- **グループの class は、そのグループの出現が持つ class のうち最も優先度の高いもの**
  （§7.4 の並び順）。各出現は自分の class と規則 ID を保持し続ける。
- **大文字小文字を区別しない集約は行わない**（トグルを置かない）。
  `C:\Data` と `c:\data` は別の行として出す。
  理由: まとめてしまうと 1 行が持つ「元の値」が 1 つに決まらず、
  §7.7 の「記録した値と完全一致」という適用条件を両方の綴りに対して満たせなくなる。
  綴りが 2 つあることは事実であり、事実のまま 2 行で見せる。
- 各行に出す（常時表示）: 値 ・ グループの class の日本語名 ・ 出現件数。
- 行を開くと第二層（出現箇所ごと）: モジュール名 ・ プロシージャ名 ・ 物理行番号 ・
  その論理行の全文（候補トークンを強調）・ 規則 ID ・
  条件付きコンパイルの内側なら「条件付きコンパイルの内側」の注記。

#### 7.5.2 `vba-highlight.js` と `vba-lexer.js` の責務境界

β2 は VBA を字句に分ける実装を**2 つ持つことになる**。既存の
`assets/js/vba-highlight.js`（93〜117 行目に独自の comment / string 判定を持つ）と、
新設の `assets/js/vba-lexer.js` である。**これは意図した二重化であり、
責務を分けることで成立させる。**

| 実装 | 用途 | 誤ったときに起きること |
|---|---|---|
| `vba-highlight.js` | **表示の着色**（diff ビュー・差分レポート HTML） | 色が少し違う。コードは変わらない |
| `vba-lexer.js` | **置換の対象決定**（候補検出・適用） | コメントや識別子を書き換える |

規律:

- **マッピング画面の根拠表示で候補トークンを強調するのは `vba-lexer.js` のスパンである。**
  `vba-highlight.js` の判定を使ってはならない。使うと「コメントとして着色されている
  文字列が置換対象として並ぶ」という、利用者から見て矛盾した画面になる。
  着色そのもの（キーワードの色など）は `vba-highlight.js` に任せてよいが、
  **候補の強調範囲は必ず `vba-lexer.js` から来る**。
- 2 つを一致させる検査は**置かない**。`vba-highlight.js` は β1.10 の表示用ヒューリスティックで、
  `100 Rem "..."` や `[Don't]` を `vba-lexer.js` ほど正しく扱わない。
  一致を要求すれば、正しい側を退化させるか、`vba-highlight.js` を作り直すことになる。
  **後者は差分レポートのバイト固定回帰（`test-diff-report-toggle.js`）に波及するため
  β2.00 のスコープ外**とする。
- したがって `vba-highlight.js` は**触らない**。責務が違うので触る理由が無い。
- 将来 `vba-highlight.js` を `vba-lexer.js` の上の描画層へ統合するのは妥当な整理だが、
  それは差分レポートの再固定を伴う別の作業である。

#### 7.5.1 プロシージャ名の決め方

字句解析の `code` トークンから宣言行を拾う。**開始だけでなく終了も追う。**

- 開始: 省略可能な `Public` / `Private` / `Friend` / `Static` に続く
  `Sub` / `Function` / `Property Get` / `Property Let` / `Property Set`。
- 終了: 対応する `End Sub` / `End Function` / `End Property`。
- 終了行より後、次の開始行より前（＝モジュールレベル）にある出現の
  プロシージャ名は `-` とする。**直近の宣言を無条件に当てない**
  （`End Sub` の後の宣言セクションが前のプロシージャに誤帰属するため）。
- 見つからなければ `-`（推測しない）。

### 7.6 マッピングの入力と検証

各行は `applied`（この行を置き換えるか）を持つ。**初期値はすべての class で `false`。**
class によって違うのは入力欄が最初から開いているか、鍵が掛かっているかだけである。

- `driveAbsolute` / `unc` / `url` / `envVar`: 入力欄は開いている。値を入れると
  `applied` が `true` になる。空にすれば `false` に戻る。
- `knownFolder` / `fragment` / `bareName` / `ambiguous`: 行内のチェック
  「この候補も置き換える」を入れて初めて入力欄が開く。チェックを入れると
  その行の第二層（根拠）が自動的に開く。

**検証は `applied` が `true` の行だけに対して行う。** `false` の行は検証対象外であり、
置換もされない。

| # | 検証（`applied` の行のみ） | 失敗時 |
|---|---|---|
| M01 | 新しい値が非空 | 行に印を付け、［置き換える］を無効 |
| M02 | 制御文字を含まない（U+0000〜U+001F と U+007F。CR / LF / TAB を含む） | 同上 |
| M03 | 長さ 1024 文字（UTF-16 コードユニット）以下 | 同上 |
| M04 | 元の class が `driveAbsolute` / `unc` / `url` のとき、新しい値が**絶対位置 3 分類**（`P-DRIVE-01` / `P-UNC-01` / `P-URL-01` のいずれか）に分類される | **要確認**の印を付け、行内チェック「入力した値が場所の形になっていないことを確認した」を入れるまで無効 |

- M04 の判定に使うのは**この 3 規則専用の分類器**であり、§7.4 の 8 分類ではない。
  新しい値が `fragment` や `bareName` に見えるかは問わない。
- **3 分類の内側での種類の変化は M04 の失敗ではない。**
  `driveAbsolute` → `url`（例: `C:\data\` → `https://…/data/`）は
  **このひな形が存在する第一の目的**（環境制約 `BOOK_PATH_IS_URL`）であり、
  確認チェックを要求しない。要求すると、機能の主目的を果たすたびに
  行の数だけ余分な操作が要ることになる。
- 種類が変わったことは**非ブロッキングの情報**として行内に 1 行出す
  （例: 「ドライブのパスから URL に変わります」）。**ゲートにしない。**
  URL 化に伴う `Dir()` / `ChDir` / `CurDir` の破綻は
  第 1 段階の診断が `DIR_EXISTENCE_CHECK` / `CURDIR_CHDIR` として既に伝えている。
  同じ判断をマッピング画面でもう一度ゲートとして課すのは、
  **ツールが良し悪しを決めること**であり §1.1 に反する。
- M04 が本当に止めたいのは「場所の形をしていない値を入れた」場合
  （例: `C:\data\` → `hello`）である。
- **`applied` の行が 1 行以上あること**が画面 4 の［置き換える］の有効条件である（§2.4）。
- 入力された値は VBA 文字列リテラルとして書き戻すとき `"` を `""` へ機械的に退避する。
  それ以外の加工（末尾 `\` の付与・正規化・大小変換）は**一切しない**。
- **自由文字列の一括置換 UI は作らない。** 置換の単位は常に「検出したトークンの集約行」であり、
  ユーザーが任意の検索文字列を入力する欄は存在しない。
- ［すべて置き換える］のような一括ボタンを置かない。

**不変条件（検証 ID ではない）**: 2 行以上が同じ新しい値を指してよい。
統合は正常な使い方であり、拒否条件を持たない。
そのため**これに失敗する fixture は存在せず、M 番号を与えない**。

### 7.7 適用（`assets/js/path-map.js`）

**必ず「全部を検査してから、全部を作って、最後に一度だけ確定する」の 3 相で行う。**
途中で状態へ書き戻さない。

**相 1 — preflight（何も変えない）**

1. 対象モジュールを**添付時のコード**から字句解析し直す（§7.7.1）。
2. `applied` の行が持つ全出現について、`(モジュール, line, column)` のトークンを取り出し、
   その値が記録した値と**完全一致**することを確認する。
3. 1 か所でも一致しなければ **E-MAP-02** で中止する。
   **このときアプリの状態は 1 か所も変わっていない**（テストで deep-equal を検査する）。

**相 2 — 再構築（コピーの上でだけ行う）**

4. 一致したトークンの**スパンだけ**を新しいリテラルへ差し替え、
   物理行をトークン列から組み立て直し、CRLF で結合して**新しいモジュール本文を作る**。
   元のモジュールオブジェクトは変更しない。
   - **列オフセットを使った逐次置換をしない。** 置換で長さが変わると後続の列がずれるため、
     常に「トークン列を作り直して 1 回で連結する」方式にする。
     この方式なら 1 行に何個あってもずれは原理的に発生しない。
5. 全モジュールの再構築が成功するまで、何も確定しない。

**相 3 — 確定（1 回だけ）**

6. 出来上がったモジュール集合を**一括で**状態へ入れる。
7. 画面と同じ `diff.js` で差分を計算し、画面 6（確認）へ進む。
   以降はビルド・検証・出力・差分レポートまで AI 経路と同一である。
8. `result.md` にマッピング表を書く（class / 旧値 / 新値 / 件数 / 出現箇所の一覧）。
9. ログには**件数・class・モジュール名だけ**を書く。値は書かない
   （パスは利用者名・サーバ名を含みうる。β1.10 §7.6 の「コード本文は記録しない」の継続）。

#### 7.7.1 やり直し（画面 6 から戻ってきたとき）

**検出と適用は同じ基準コードを読む。** 基準は検出したときに `state.pathMapBasis`
へ記録され、適用はそこからしか読まない（`getPathMapBaseModules()`）。

| そのときの状態 | 基準 |
|---|---|
| ひな形を選んだ／選び直した | 添付時のコード（`attachBook` が返した `module.code`） |
| AI の改修返答を取り込んだあとに検出した | その返答のコード |

**前回の置換結果を基準にしない。** すると旧い値がすでに消えているために
E-MAP-02 が必ず起き、値を直して置き換え直す操作が必ず失敗する。

- 画面 4 へ戻った時点で、マッピングの入力内容（`applied` と新しい値）は保持する。
- ［次へ］を押し直すと、記録した基準から作り直した結果で
  **前回の置換結果を丸ごと置き換える**。
- そのとき手動修正（画面 7 の編集）が残っていれば、
  **実行前に確認ダイアログを出す**（β1.10 の `edit-discard-modal` と同じ型）。
  ［破棄して置き換える］を押したときだけ進む。黙って捨てない。

### 7.8 内部契約（将来の汎用マッピングのために固定する）

```json
{
  "schemaVersion": 1,
  "templateKey": "fixed-path-replace",
  "rows": [
    {
      "groupKey": "C:\\data\\",
      "class": "driveAbsolute",
      "from": "C:\\data\\",
      "to": "https://contoso.sharepoint.com/sites/eigyo/Shared Documents/data/",
      "applied": true,
      "occurrences": [
        { "module": "MonthlyReport", "procedure": "LoadSource", "line": 42, "column": 21,
          "class": "driveAbsolute", "ruleId": "P-DRIVE-01", "inConditional": false }
      ]
    }
  ]
}
```

- `groupKey` は**値そのものだけ**（§7.5）。`class:値` にしない。
- `rows[].class` は**そのグループの出現が持つ class のうち最も優先度の高いもの**。
- `occurrences[].class` と `ruleId` は**出現ごとの**分類であり、`rows[].class` と
  異なることがある（同じ値が文脈によって別の class に当たるため）。
- `occurrences[].line` は 1 起点、`column` は 0 起点 UTF-16 コードユニット（§7.3.1）。
- `inConditional` は `#If`〜`#End If` の内側かどうか（§7.3 / §7.5 の根拠表示に使う）。

この形は engine に依存しない。将来ほかの決定的置換（接続文字列・プリンタ名など）を
足すときも、同じ `rows` 構造と同じ画面部品を使い、`templateKey` と検出規則だけを替える。
**その拡張は β2.00 のスコープ外である。**

### 8.4 ログ

追加で記録する事象:

- 環境定義の読み込み（`profileId` / `revision` / `constraints` 件数、失敗時は理由）
- 診断パッケージの受理・拒否（拒否は検査番号 D01 等。**本文は記録しない**）
- 決定的置換の適用（class ごとの件数、対象モジュール名。**値は記録しない**）
- 依頼 ID の生成が `Math.random` へ fallback したこと（[AUDIT-BETA1.md](beta2/AUDIT-BETA1.md) §1.4.1 A3）
- クリップボードの再試行が発生したこと（回数と最終結果。§8.5）

### 8.5 クリップボードの競合耐性

**背景（実測）**: codex-implementer が β1.10 の実 WebView2 試験を走らせたところ、
`test-flow-webview.ps1` が 3 回連続で失敗した。原因は製品のアサーション到達前に
WPF の `Clipboard.SetText` / `GetText` が `0x800401D0`（`CLIPBRD_E_CANT_OPEN`）を
返したことで、試験後の `GetOpenClipboardWindow` は 0 だった。
つまり**恒常的な占有ではなく、他プロセスとの一時的な競合**である。

β2.00 は AI との受け渡しをクリップボードと添付ファイルで行い続ける（§11）。
受け渡しは一本道の途中に**2 回**ある（診断依頼・改修依頼）ため、
β1.10 より競合に当たる機会が増える。したがって次を製品側に入れる。

1. **有界の再試行**: `04_HostServices.cs` の `Clipboard.SetText` / `GetText` を
   **最大 10 回呼び出す**（＝待ちは最大 9 回・各 50ms・合計 450ms）。STA スレッド上のまま。
   利用者から見て「固まった」と感じる長さにしない。
   - **再試行するのは `HRESULT 0x800401D0`（`CLIPBRD_E_CANT_OPEN`）だけ。**
     それ以外の例外は 1 回目で即座に失敗させる。
     区別しない再試行は、本当の失敗を 450ms 遅らせるだけで何も救わない。
   - 実装は再試行の中身を差し替えられる内部ヘルパー
     （操作を delegate で受ける形）にする。テストが呼び出し回数と HRESULT を
     決定的に検査できるようにするためで、実クリップボードの占有再現に依存させない。
   - **各回で占有者を記録する**: 再試行のたびに `GetOpenClipboardWindow()` を取り、
     0 でなければ `GetWindowThreadProcessId` からプロセス名と PID を得る。
     最終失敗時に WARN でログへ残す。
     **450ms を超える競合は実測で確認済み**（[DECISIONS-BETA2.md](beta2/DECISIONS-BETA2.md) D-14）
     なので、「誰が掴んでいたか」は利用者にとっても運用にとっても必要な事実である。
     ログにはプロセス名と PID だけを書く（ウィンドウタイトルは書かない。
     他アプリの文書名が漏れうるため）。
2. **最後まで失敗したら事実として出す**: 書き込み失敗は既存の `E-GEN-03`、
   読み取り失敗は新設の `E-GEN-04`。**黙って成功にしない・黙って空文字を返さない。**
   β1.10 の `readClipboard` は空を `{text:""}` として返すが、
   これは「空だった」ときの正常応答であり、**例外を空へ潰してはならない**。
3. **復旧の導線を画面に出す**: コピー失敗のトーストに「もう一度コピー」を、
   取り込み失敗のトーストに「`Ctrl+V` でも貼り付けられます」を添える。
   `Ctrl+V` の `paste` イベント経路は OS のクリップボード API を通らないため、
   ボタン経路が競合で落ちても貼り付けは成立する（β1.10 §7.3 の二経路がここで効く）。
4. **試験側**: 実 WebView2 試験のクリップボード操作にも同じ有界再試行を入れる。
   **再試行を尽くしても失敗したら試験は失敗させる**（緑にするための緩和ではない）。
   再試行が発生した回数を試験ログへ出し、フレークを見えなくしない。

| `## 用途` | — | **廃止**。段階はフォルダが決めるため、ファイルが名乗る必要が無くなった |

**分割の見出しは段階ごとに別の名前で、互いに排他である。**

|---|---|---|
| `01_診断/` | `## 出力指示（分割）` | `## 出力指示（モジュール単位）` |

**同梱の改修ひな形 3 本がその見出しを現に持っており、改称は文面の移行を伴うだけで
機能上の利得がゼロだから**である。分けるのは「診断の分割」と「改修の分割」が
別の契約（§4.7 と β1.10 §6.6）だからであり、名前を揃える必要はない。

`## 用途` を持つファイルは **E-PRESET-01**（「`## 用途` は使わなくなりました」を message に出す）。
黙って無視しない。

#### 9.2.1 変更範囲のファイル

`presets/03_変更範囲/*.md` に使える見出しは `## 説明`・`## 構造変更`・`## 改修指示`
の 3 つだけで、3 つとも必須である。ほかの見出しは E-PRESET-01。

`## 出力指示` を持たないのは、変更範囲が単独で AI へ話しかけないからである。

選択肢を置かない。読者に二重否定を読ませないためである。

### 13.1 技術構成

**PowerShell 5.1 + Add-Type(C#) + WPF + WebView2** のハイブリッド構成。

- `launch.vbs` で黒画面を一切出さずに起動。配布物の起動方法は launch.vbs
  ダブルクリックの一択（開発時のみ launch.bat でコンソール表示）。
- UI の実体は WebView2 内の HTML/CSS/JS。XAML（WPF）は殻。
- dotnet SDK 不要。フォルダをコピーするだけで動くこと。
- WebView2 DLL（SDK 1.0.3856.49）をリポジトリに同梱する。

### 13.2 外部依存を持たない

MacroStudio は単体で完結し、実行時に外部ライブラリを必要としない。

- VBA の抽出・書き戻し（OLE2 複合ドキュメントの読み書き、MS-OVBA 圧縮ストリームの
  展開・再圧縮）は **MacroStudio 自身の実装**として `src/` に持つ。
- diff アルゴリズムと VBA シンタックスハイライトも自前実装（`assets/js/`）。
- 実行時依存はリポジトリ同梱の WebView2 DLL と OS 標準コンポーネントのみ。

### 13.3 エンジンの実装位置

エンジン（OLE2 / VBA 圧縮 / 書き戻し）は、ホストと同じ Add-Type でコンパイルする
**C# クラスとして src/ 内に実装**する（子プロセスや別モジュールを作らない）。

理由:
- 中核はバイト列処理であり、C# で書くのが最も素直。
- 子 PowerShell プロセス + JSON ファイル受け渡しの複雑さ（起動待ち・文字コード・
  一時ファイル管理）が丸ごと消える。
- GUI から切り離した検証は、同じ src/*.cs を Add-Type するヘッドレスの
  テストスクリプト（tests/）で行える。

### 13.4 対応ファイル形式

判定は**拡張子ではなくファイルの中身**で行う。拡張子は入口のブロッカーにしない。

| 拡張子 | 中身 | 扱い |
|---|---|---|
| `.xlsm` | zip 内 `xl/vbaProject.bin`（OLE2） | 対応 |
| `.xlam` | 同上 | 対応 |
| `.xlsb` | 同上 | 対応。機構上は xlsm と同一経路（§15） |
| `.xls`  | ファイル全体が OLE2 | 読み取り対応。ビルドは検証（§9）を通った場合のみ成功 |
| その他 | — | zip なら vbaProject.bin を、OLE2 なら本体を VBA コンテナとして読む。どこにも VBA が無い場合だけ E-ATTACH-03 |

補足:
- VBA プロジェクトにパスワード保護が掛かったブック: 保護は VBE の閲覧ゲートであり
  モジュールストリーム自体は暗号化されない（MS-OVBA 仕様）ため、抽出・書き戻しとも
  影響を受けない**見込み**。実ファイルでの確認は未実施（§15）。

#### 13.4.1 ファイル全体が暗号化されたブック

「開くときのパスワード」が掛かったブックは中身が読めないので、**読み取り成功にせず
attach を止める**（E-ATTACH-04。§12）。

判定: ファイルが OLE2 で、**ルートストレージ直下に `EncryptedPackage` と
`EncryptionInfo` の両方のストリームがある**場合だけ暗号化とみなす（MS-OFFCRYPTO。
Excel が実際に書き出したファイルで確認した形）。ディレクトリは通常の OLE2 リーダで
読む。バイト列の走査はしない。片方だけ、OLE2 として解析できない、
のいずれでも暗号化とは判定しない（破損ファイルを暗号化扱いにしないため）。

上の VBA プロジェクト保護（DPB / CMG）とは別物である。あちらは `vbaProject.bin`
内部の PROJECT ストリームの話で、ファイル自体は暗号化されていないため、この判定に
掛からない。**暗号化ブックで「全モジュール読み取れています」を出してはならない。**
読取レポート（§13.6）には到達せず、画面には理由と対処（Excel でパスワードを外した
コピーを保存し、それを読み込む）を出す。

### 13.5 VBA 読取の 6 経路

上から順に試し、**モジュールが 1 つでも読めた時点で採用**する。後段へ落ちた場合は
警告（`warning:true`）を 1 度だけ出し、操作は継続する。

| # | 経路 | 使う場面 |
|---|---|---|
| 1 | ZipArchive で `vbaProject.bin`（名前一致 → 大小無視 → `.bin` かつ VBA ストレージを持つもの） | 正常な xlsm / xlam / xlsb |
| 2 | ZIP central directory を自前で走査して local header から取り出す | EOCD やアーカイブ構造が壊れている |
| 3 | ファイル全体から local file header を走査（stored / deflate 双方） | central directory が失われている |
| 4 | ファイル先頭が OLE2 署名ならファイル自体をコンテナとみなす | xls など |
| 5 | ファイル中の任意位置の OLE2 署名から VBA コンテナを探す | 非圧縮格納されたメンバなど |
| 6 | 生バイトから MS-OVBA 圧縮コンテナを走査し、`Attribute VB_Name` を持つものをモジュールとして復元 | CFB directory ごと壊れている |

モジュール単位でも同様に多経路で読む。dir の MODULEOFFSET を使い、そこに
`Attribute VB_Name` が無ければストリームを後方から再走査する。1 つのモジュールの
失敗が他のモジュールを巻き込まないよう、モジュール単位で例外を閉じる。
dir が壊れていれば PROJECT ストリームの列挙を、PROJECT も壊れていれば VBA ストレージ
配下のストリームを直接読む。

新規モジュール追加は dir / PROJECT / PROJECTwm を書き換えるため、**3 者が厳密に読めて
互いに一致している場合だけ**有効にする（`ProjectModulesOffset` を保持する条件）。
書き込み時の文字コード変換は常に厳密（表現できない文字はビルド失敗にし、
置換文字をブックへ書かない）。

### 13.6 読み取り結果の 2 段階

上の多経路読取は、規格どおりでない箇所を見つけるたびに記録して先へ進む。その記録は
約 70 か所から立つ 1 つの真偽値（`HasReadWarnings`）だが、**内容の意味は 2 種類しかない**。
どちらなのかを分けずに 1 つの警告にすると、直す必要のないブックまで不安にさせるため、
次の事実を別に持ち、表示を分ける。

| 記録する事実 | 意味 |
|---|---|
| モジュールの圧縮ソースを厳密展開できず best-effort 展開した | そのモジュールのコードが途中までの可能性がある |
| OLE2 ストリームが記録サイズより短く返った | 内容の欠落 |
| 容器構造が残っておらず生バイトから復元した（salvage） | 内容の欠落の可能性 |
| 一覧にあるのにソースを読めなかったモジュールがある | そのモジュールが一覧から落ちている |
| vbaProject.bin を通常以外の経路で取り出した（名前の大小・`.bin` 推測・central directory 走査・生走査・埋め込みコンテナ） | 取り出し経路の話。中身のコードには関係しない |
| dir の MODULEOFFSET がソースを指さず、ストリームを走査して見つけた | 位置情報だけの不一致。コードは完全に展開できている |
| CFB / dir / PROJECT / PROJECTwm の管理情報が規格どおりでない（ヘッダ値、FAT/DIFAT/miniFAT の帳簿、件数・種類・名前一覧の不一致） | 読み取ったバイト列には影響しない |

表示は 2 段階とする。

- **コードに疑いがある**（上表の前半 4 つのいずれか）… 原因を断定せず、
  「一部をバイナリレベルで読み取れませんでした。」＋該当モジュール名＋
  「改修前後のコードを確認してください。」を注意として出す。
- **管理情報だけ**（それ以外）… 「マクロのコードは全モジュール読み取れています。」を
  お知らせとして出し、何が規格どおりでなかったかを 1 行添える。コードへの影響が
  無いことを述べ、対処を求めない。
- ホストが内訳を返さない場合は切り分けられないので、前者の控えめな文言を使う。
- **どちらの場合もブックの読み込みは成功**であり、正常なブックを拒否する分岐は持たない。
  外部リンク切れなど VBA 以外のパートの問題は、読取器が `vbaProject.bin` しか開かない
  ため、そもそもこの記録に現れない。
- 表示場所は attach 直後のトースト 1 回と、画面 0 の見出し直下および
  「読み取った内容を見る」の統計（`コードの読み取り`）。

### 13.7 コード全文ファイル（固定形式）

コードファイルの形式はツール側で固定し、テンプレートでは変更できない
（チャット AI が正常に読める形式を、互換性の契約として保護するため）。
出力は UTF-8 BOM 付き、改行は CRLF、末尾は CRLF 1 個とする。

構成（見出し等の固定文字列はすべて ASCII）:

1. 80 桁の `=` 罫線で挟んだヘッダ: ` <ブック名> - VBA Source Code` と
   ` Generated: <yyyy-MM-dd HH:mm:ss>`。
2. `MODULE INDEX` と 40 桁の `-` 罫線。種別ごと
   （Standard Modules / Class Modules / UserForms / Document Modules）に
   `    <名前>.<拡張子> (<行数> lines)` を列挙し、
   `  Total: <合計行数> lines across <モジュール数> modules` で締める。
3. モジュールごとに、80 桁の `=` 罫線で挟んだ ` <名前>.<拡張子>` 見出しと、
   Attribute ヘッダ除去済みのコード全文（§13.8）。空のモジュールは見出しだけを
   出し、本文や注記は書かない（空であることはプロンプト側の一覧で伝える）。

### 13.8 Attribute 行の扱い

- 抽出時: 各モジュール**先頭の連続した** `Attribute VB_*` 行群（ヘッダブロック）を
  分離して保持し、画面表示・コードファイルには**含めない**（VBE でも見えない行であり、
  使用者とチャット AI の双方にノイズのため）。コード途中のプロシージャ属性
  （`Attribute xxx.VB_UserMemId` 等。稀）はコードの一部としてそのまま残す。
- 同梱ひな形の出力指示でチャット AI にも「先頭に Attribute 行を付けない」よう指示（§9.2）。
- 貼り付け時: 万一先頭に含まれていても機械的に除去（§13.13。先頭ブロックのみ。
  抽出時と同じ規則にすることで、コード途中の属性を巻き添えにしない）。
- ビルド時: 保持しておいた**元のヘッダをそのまま先頭に再付与**して書き戻す。
  `Attribute VB_PredeclaredId` 等の意味を持つ属性が失われることを防ぐ。
- 新規標準モジュールだけは、C# 側で `Attribute VB_Name` を生成する。
- 帰結として既存モジュールの Attribute 行は変更できない（用途上不要。§11）。

### 13.9 改修返答パッケージの基礎形式

AI の返答は、変更したモジュールと新しく作ったモジュールの全文を**ちょうど 1 つの
コードブロック**にまとめたものとする。取り込みは 1 回の操作で全体を読む（§5.4）。

**依頼 ID（request nonce）**: 改修依頼を生成する時点でアプリが UUID v4 を 1 つ発行する。
乱数であり、コードや依頼文から計算されるハッシュではない。AI にハッシュや
チェックサムを計算させることはしない（ひな形にもそう書かない）。
ID は依頼プロンプトの区切り行の中に埋め込まれ、返答はそれをそのまま書き写す。

**区切り行**: 行全体が区切りである場合だけ区切りとして扱う（前後の空白は無視）。

```
'@MACROSTUDIO <依頼ID> SUMMARY BEGIN
（何をどう直したかの要約。マクロを書かない人にも分かる言葉で）
'@MACROSTUDIO <依頼ID> SUMMARY END
'@MACROSTUDIO <依頼ID> BEGIN <種類> <モジュール名>
（そのモジュールの全文）
'@MACROSTUDIO <依頼ID> END <種類> <モジュール名>
'@MACROSTUDIO <依頼ID> COMPLETE <モジュールの数>
```

- 先頭が `'` なので、区切り行はそのまま VBA のコメントとして正しい。
- `<種類>` は `standard` / `class` / `form` / `document`。
- モジュールの中に `'@MACROSTUDIO ...` に似た文字列があっても、行全体が
  この依頼 ID を持つ区切りでない限りモジュールは終わらない。曖昧な文字列分割は
  しない。
- コードフェンス（``` 行）は有っても無くてもよい。モジュールの外側にある行は
  読み飛ばし、モジュールの中の行はそのまま取り込む。
- SUMMARY の中身は散文であり、コードとして扱わない。取り込み画面の
  「AIが書いた改修内容を見る」で表示するだけで、ブックへは書き戻さない。
  要約をコードブロックの外へ書かせないのは、使用者がコピーするのが
  コードブロックだけだからである。SUMMARY が無い返答も取り込みは成功し、
  その場合は要約の開閉が出ないだけになる。

**検証**（`assets/js/response-package.js` が唯一の実装。1 つでも通らなければ
何も取り込まない）:

| 検査 | 断る理由 |
|---|---|
| 依頼 ID がこの依頼のものか | 別の依頼への返答 |
| 区切りが 1 つでもあるか | 取り込める形が無い |
| BEGIN と END が 1 対 1 で対応するか | 区切りが揃っていない |
| BEGIN の入れ子が無いか | 区切りが揃っていない |
| `COMPLETE` があるか | 返答が途中で切れている |
| `COMPLETE` の数とモジュール数が一致するか | 区切りが揃っていない |
| 同じモジュールが 2 回無いか | 重複 |
| `<種類>` が既知か | 知らない種類 |
| モジュール名が VBA 識別子として妥当か | 使えない名前 |
| 各モジュールの中身が空でないか | 中身が無い |
| SUMMARY が閉じているか / 入れ子でないか | 区切りが揃っていない・途中で切れている |

**モジュールの種類の正本**:

- 既存モジュールは**ブック側の種類が正本**。返答の `<種類>` が食い違っても
  ブックの種類のまま取り込み、画面 6 に常時表示の警告として何を読み替えたかを出す。
  返答の言い分でモジュールの型を変えることはしない。
- 新規モジュールは**標準モジュールのみ**受け付ける（§13.14）。
  `class` / `form` / `document` の新規追加は取り込みを断る。

失敗時は例外文・エラーコード・記号を画面に出さず、次にどうすればよいかを 1 文で
伝える（E-INTAKE-01）。ログには理由コードを残す。

変更モジュールが 0 件の返答は §5.4.1 に従う。`UNNECESSARY` / `IMPOSSIBLE` /
`UNCLEAR` のいずれも暗黙の空返答へ格下げせず、明示された契約だけを受理する。

### 13.10 改修のモジュール単位出力（任意）

長い実務マクロでは、変更モジュール全部を 1 回の返答に収めきれず途中で切れることが
ある。そのための**任意オプション**であり、既定でも主経路でもない。既定は §13.9 の
ワンペースト方式のままで、この節はそれを置き換えない。

**選び方**: 画面 5（改修依頼の受け渡し）に「モジュール単位出力（コードが長い時用）」を置く。
選んだひな形が `## 出力指示（モジュール単位）`（§9.2）を持つときだけ出る。
ON にすると、依頼プロンプトへ差し込む出力指示がその節の本文に替わる。
依頼文・コードファイル・添付方法・実行フォルダは何も変わらない。
切り替えると、それまでに取り込んだ内容は破棄する（2 つの返し方を混ぜない）。

**返答の形**: 1 回の返答が 1 つのコードブロックで、その中は**ちょうど 1 モジュール**。
何番目かと総数を名乗る区切り行が 1 本増える。ほかは §13.9 と同じで、
`COMPLETE` は毎回 `1` になる。

```
'@MACROSTUDIO <依頼ID> SUMMARY BEGIN      … 1 回目だけ
（何をどう直したかの要約）
'@MACROSTUDIO <依頼ID> SUMMARY END
'@MACROSTUDIO <依頼ID> PART <番号> OF <合計>
'@MACROSTUDIO <依頼ID> BEGIN <種類> <モジュール名>
（そのモジュールの全文）
'@MACROSTUDIO <依頼ID> END <種類> <モジュール名>
'@MACROSTUDIO <依頼ID> COMPLETE 1
```

- `<番号>` は `00` から始まる 2 桁。`<合計>` は変更するモジュールの総数（2 桁）。
- 1 回目は番号 `00` を出し、コードブロックの**外**で「次のモジュール 01 を
  出してよいか」を確認させる。以後 `01`、`02` … と `<合計>` に達するまで
  1 回に 1 つずつ繰り返させる。全モジュールを 1 回にまとめさせない。
- この進め方の文面はひな形の `## 出力指示（モジュール単位）` が持つ。ツールも
  テンプレートも同じ文面を持たない（§1.2 / §9.2）。

**取り込み**: このモードのときだけ画面 6 で複数回受け取り、`response-package.js`
が機械的に 1 つの変更一式へ統合する。統合は帳簿付けであり、解釈ではない
（コード本文から番号・名前・種類を推測することはしない）。

1. 各返答を §13.9 の規則で解析する。加えて `PART` 行が 1 本あることと、
   モジュールがちょうど 1 つであることを確認する。
2. 受け取り済みの分と照合する（下表）。1 つでも通らなければ**その返答を
   取り込まず**、集めた分は変えない。
3. 画面には「2 / 4個を受け取りました」と、受け取り済みの番号・モジュール名、
   まだ届いていない番号を出す。全部そろうまで［次へ］は無効。
4. `00` から `<合計>-1` まで全部そろった時点で、番号順に 1 つのパッケージへ
   まとめ、§13.9 の取り込みと**まったく同じ経路**で適用する（種類はブックが正本、
   新規は標準モジュールのみ、§13.13 の正規化、diff 計算）。以後の確認・ビルド工程は
   ワンペースト方式と同一である。
5. SUMMARY は届いた分を番号順に連結して「AIが書いた改修内容を見る」へ出す。

| 検査 | 断る理由 |
|---|---|
| 依頼 ID がこの依頼のものか | 別の依頼への返答 |
| `PART` 行があるか | 何番目か分からない |
| `PART` 行が 1 本だけ・`<番号>` < `<合計>`・数字が読めるか | 区切りが揃っていない |
| モジュールがちょうど 1 つか | 1 回に複数のモジュールが入っている |
| `<合計>` が前の返答と同じか | 総数が食い違っている |
| 同じ番号が前と違う内容で来ていないか | 内容の異なる重複 |
| 同じモジュールが別の番号で来ていないか | 重複 |

- 同じ番号・同じモジュール・同じ内容の再ペーストだけは、受け取り済みとして
  何も変えずに受け入れる（同じ操作を繰り返しても状態が壊れない）。
- 内容の異なる同番号は断る。やり直すときは［最初から取り込み直す］で集めた分を
  空にしてから、番号 `00` から入れ直す。
- **欠番のまま先へ進むことはできない**。番号が足りなければ［次へ］が無効のままで、
  何が足りないかを画面が名指しする。
- オプションが OFF のときに `PART` 行付きの返答を貼った場合は取り込まず、
  画面 5 でオプションを選ぶよう 1 文で伝える。逆に ON のときに `PART` 行の無い
  返答（ワンペースト形）を貼った場合も取り込まない。

### 13.11 差分 HTML は確認画面の閲覧専用版

差分 HTML は**確認画面（§5.5）の diff をそのまま持ち出したもの**とする。見た目・
情報構成・操作を画面と揃えるため、レポートは**画面と同じ実装を同梱して描画する**。

- 同梱するもの: `assets/js/diff.js`・`vba-highlight.js`・`diff-view.js` と
  `assets/css/variables.css`・`flow.css`・`module-list.css`・`diff.css` を
  **無加工でインライン**する。加える加工は 1 つだけで、`@font-face` 宣言の除去
  （出力フォルダからは相対 url を解決できないため。トークン側の代替フォントに落ちる）。
- レポート側が持つのは枠だけ（モジュール一覧・ツールバー・テーマ切替・実行データ）。
  行の作り方、文脈行数、変更ブロックの数え方、`変更箇所のみ` の規則は**画面側の
  実装が唯一の正本**であり、レポート側に第 2 実装を置かない。
- 表示するもの: モジュール名・モジュール種別・変更行数、インライン diff。
- 動く操作: ［↑ 前の変更］［↓ 次の変更］と件数表示、［変更箇所のみ］、［折り返し］、
  ライト／ダーク切替、モジュール一覧からの切り替え。畳んだ箇所の「…N 行を表示」も
  画面と同じく展開できる。
- **高さ制限を持たない**。画面はフロー内の固定高ペインに diff を収めるが、レポートは
  文書全体が diff の高さまで自然に伸びる。横に長い行だけが横スクロールする。
- 「変更内容を見る」の折りたたみは持たず、最初から diff を表示する。
- **編集操作を一切持たない**。手動修正・編集用チェック・編集オプション・改修概要欄は
  置かない（`textarea` / `input` / `contenteditable` が 1 つも無いことをテストで固定）。
- 既定は全行表示・折り返しあり・ライトテーマ。長いモジュールは画面と同じ規則で
  最初から［変更箇所のみ］になる。
- **自己完結**: 外部 CSS / JS / フォント / 画像 / 通信を持たない。実行データは
  `<script type="application/json">` の島で運び、`<` を必ず退避してコードが
  タグを閉じられないようにする。
- script を持たない版から**自己完結インライン JS を持つ版へ改める**。理由は上記の
  操作をローカル単体ファイルで成立させるためであり、境界は変わらない
  （外部通信なし・編集なし・アプリへ戻る経路なし）。スクリプトを無効にして開いた
  読者には `<noscript>` で理由を伝える。
HTML の生成・書き込みだけが失敗した場合はログとエラートーストに通知するが、
完成済みブックの成功は取り消さない。`result.md` の書き込みだけが失敗した場合も
同じ扱いとし、差分レポートと同様に完了画面と通知へ出す（片方だけ黙らせない）。

ビルド後も［戻る］で取り込みや依頼へ戻って続きの改修 → 再ビルドができる。
実行フォルダは依頼作成時点で確定しているため、再ビルドは**同じフォルダの中で
自分が作った成果物（改修済みブック・差分レポート・`result.md`）を
1 つの世代として置き換える**。

- 置き換えの対象は、**このアプリがこの実行で作ったファイルだけ**である。
  同名でもアプリが作っていないファイルは触らず、E-BUILD-03 で止まる。
- 改修済みブックは同じフォルダの作業名で組み立て、読み直し検証に合格した
  ときだけ本来の名前へ差し替える。失敗した再ビルドは前の世代を壊さず、
  作業ファイルも残さない（all-or-nothing を再ビルドでも保つ）。

### 13.12 ホスト境界

#### 13.12.1 WebView2 の境界

同梱ページだけを製品として扱い、それ以外は境界で拒否する。判定と設定は
`src/02_WebViewSecurity.cs` の 1 か所が持ち、製品も WebView2 テストも同じ実装を通る。

**信頼 origin** は `https://macrostudio.local`（scheme・host・既定ポートの完全一致）。
`SetVirtualHostNameToFolderMapping` で `assets/` に割り当てている唯一の origin である。
前方一致では判定しない。`https://macrostudio.local.example.com/`、
`https://macrostudio.local:8443/`、`http://macrostudio.local/`、資格情報付き URI、
空文字・相対・解析不能な値はすべて信頼しない。

| 経路 | 扱い |
|---|---|
| `WebMessageReceived` | `e.Source` が信頼 origin と完全一致しなければ、**JSON を読む前に**破棄する。`Dispatch` へ到達させず、応答も返さない（信頼外へ手掛かりを返さないため）。拒否は `WARN` でログに残す |
| `NavigationStarting` | 信頼 origin 以外を `Cancel`。http / file / data / about / 別ホストはすべて対象。**起動時の例外許可は持たない**（実測の結果、ランタイムが要求する遷移は製品ページのみだった） |
| `FrameNavigationStarting` | 同じ判定で `Cancel`。アプリは frame を使わない |
| `NewWindowRequested` | `Handled = true` にして開かない。外部ブラウザへの転送も行わない |

**設定**: `AreDevToolsEnabled = false`、`AreBrowserAcceleratorKeysEnabled = false`
（F12・Ctrl+Shift+I・Ctrl+R 等。Ctrl+C/V/X/A などの編集キーは対象外で、
取り込み画面の貼り付けは動く）、`AreDefaultContextMenusEnabled = false`、
`AreHostObjectsAllowed = false`（アプリは host object を 1 つも追加しない）。
`IsWebMessageEnabled` は製品機能なので有効のまま。

#### 13.12.2 ドラッグ＆ドロップ

WebView2 はクライアント領域全面を占める子ウィンドウを持つため、外部ドロップは
**まず WebView2 が受け取る**。`AllowExternalDrop = false` にすると WebView2 が
ドロップを拒否し、WPF 側の `Drop` にも届かない（実機で D&D が無反応だった原因）。
したがって次の構成で実装する。

1. **方式B（主経路）**: `AllowExternalDrop = true` を設定し、ページ側の
   `dragover`/`drop` で `chrome.webview.postMessageWithAdditionalObjects()` を使って
   `File` を host へ渡す。host は `e.AdditionalObjects` の `CoreWebView2File.Path`
   からフルパスを読み、`resolveDroppedFiles` の応答として JS へ返す。JS は通常の
   attach 経路（確認ダイアログ・警告表示を含む）でそのパスを添付する。
   （`postMessageWithAdditionalObjects` / `CoreWebView2File` は SDK 1.0.3856.49 対応）
2. **方式A（副経路）**: WPF 側 `PreviewDragOver`/`PreviewDrop` は残す。ページに届かない
   ドロップ（ウィンドウ枠など）を `DataFormats.FileDrop` から拾い、`bookDropped`
   イベントで JS へ渡す。
3. **方式C（常設の保険）**: 「ファイルを選ぶ」ボタン（OpenFileDialog）。

ドラッグ中は `body.is-file-drag` を付け、ドロップ先が分かるようにする。
MacroStudio と Explorer の整合性レベルが異なる場合（片方だけ昇格実行）は UIPI により
OS がドロップ自体を拒否する。この場合は方式C を使う。

#### 13.12.3 host request の待ち方

`host-bridge.js` は id 付き request/response を Promise で解決する。既定は
120 秒で pending を捨てて E-SYS-02 で reject する。これは「すぐ返るはずの action が
返らなかった」ことを事実として返すための界である。

ただし**ビルドはこの界の対象にしない**。ビルドは元ブック全体の再読・コピー・
再構築・書込・再検証を行い、大容量ブックや低速なドライブ、ウイルス対策の走査では
120 秒を超えることがある。host 側は cancellation を持たず最後まで走るため、
client の時計で失敗を確定させると「出力は作成していません」と表示した後で
出力が現れる、という観測と食い違う状態を作る。したがって:

- `buildBook` は `timeoutMilliseconds: 0`（reject する timer を持たない）で送る。
  **処理の正本は host の応答**であり、成功・失敗はそれだけが決める。
- 120 秒の時点では reject せず、「時間がかかっています。処理は続いています」を
  トースト・読み上げ・ビルド画面の案内に出す（`state.buildSlow`）。
  pending entry は残るので、遅れて届いた応答は同じ request ID で解決される。
- その間 `busyAction` は解除しないので、［戻る］［次へ］［もう一度ビルドする］は
  押せない。同じ出力へ 2 つのビルドが並行することはない。
- host へ cooperative cancellation は送らない。書込途中の中断は出力破損の経路を
  増やすためで、代わりに「終わるまで待ち、結果を事実として出す」を選ぶ。
  これは owner が選んだ無界の待ちであり、待っていることを画面に出して隠さない。

#### 13.12.4 ログの基礎契約

- 出力先: `%LOCALAPPDATA%\MacroStudio\logs\macrostudio_<yyyyMMdd>.log`（追記、UTF-8）。
- 書式: `[HH:mm:ss] [LEVEL] message`。
- 記録する事象: 起動/終了、attach（パス・モジュール数）、コードファイル生成（パス）、
  貼り付け（モジュール名・行数のみ。**コード本文は記録しない**）、ビルド開始/結果、
  すべてのエラー（スタック含む）。

### 13.13 貼り付けテキストの正規化

貼り付け時に次の規則を**この順で**機械的に適用する。これは §1.2 の「帳簿付け」であり、
ここに列挙した以外の加工をしてはならない。

1. 改行を CRLF に正規化する。
2. 行頭が ``` で始まる行（コードフェンス）を削除する
   （チャット AI のコピーボタンではなく手動範囲選択でコピーした場合の保険）。
3. **先頭から連続する** `Attribute VB_` 行（大文字小文字無視、行頭空白許容。
   間の空行は許容して読み飛ばす）を削除する（§13.8 と同じ「先頭ブロックのみ」規則。
   コード途中の Attribute 行には触れない）。
4. 先頭・末尾の空行を除去し、末尾に CRLF を 1 つ確保する。

正規化の結果はそのまま右ペイン・diff に出る（使用者から見て隠れた加工にしない）。
正規化後が空文字列なら貼り付け不成立（E-PASTE-01）。

ビルド直前の結合（JS 側）: 既存モジュールは
`保持していた Attribute ヘッダ + CRLF + 正規化済みテキスト` を最終コードとして渡す。
新規標準モジュールは可視コードと `isNew:true` を渡し、C# 側で `VB_Name` を生成する。

### 13.14 新規モジュールは標準モジュールだけ

- 共通処理を既存モジュールへ重複して置かず、新しい標準モジュールへ分離できる。
- 名前と種類は返答パッケージの区切り行が名乗る（§13.9）。区切りの検証を通った
  ものだけを取り込み、コード本文から名前や種類を推測することはしない。
- OLE2 の新規ストリーム、dir の MODULE レコード、PROJECT の `Module=` 行、
  PROJECTwm の NAMEMAP を一括して追加し、§14.1 の読み直し検証を通す。
- **新規追加は標準モジュールのみ**。writer は `Module=` / dir type 0x0021 /
  `VB_Name` だけを生成し、読み直し検証も追加物を Standard として確認する。
  返答が `class` / `form` / `document` の新規追加を含む場合は取り込みを断り、
  ひな形の出力指示にも「新しく増やすモジュールは標準モジュールだけ」と明記する。
- **既存モジュールの改修は種類を問わない**。クラスモジュールも含めて改修でき、
  抽出時の属性ヘッダー（`VB_PredeclaredId` / `VB_Exposed` など）を再結合して
  書き戻し、読み直し検証で種類を問わずコード一致を確認する
  （`tests\test-monthly-report-roundtrip.ps1` と `tests\test-class-roundtrip.ps1`）。
- 削除・名前変更は対象外。

### 13.15 テーマと入力中の描画

- 色、字、間隔、角丸、影、寸法は `assets/css/variables.css` の意味トークンを正本とする。
  ライトを既定とし、ダークの選択は `localStorage` の `macrostudio.theme` へ保存して
  初回描画前に復元する。両テーマは独立にコントラストを満たす。
- UI は同梱の Noto Sans JP、コードと diff は UDEV Gothic を使う。差分 HTML は
  同じトークンを内蔵し、フォントを解決できない場所では代替フォントへ落ちる。
- 画面は状態から組み立てる。ただし同じ画面の `input` / `textarea` / `select` /
  `contenteditable` がフォーカスを持つ間は、その要素を DOM から外さない。
  `renderMain` は既存要素へ属性と周辺表示の差分だけを当て、本人が入力中の欄へ
  `value` / `checked` を書き戻さない。
- 「再描画後に focus を戻す」方式は採らない。IME の composition、caret、選択範囲は
  同じ要素が生きていることに依存する。希望動作、追加の要望、マッピングの新値、
  出力名を含む全編集要素が同じ規律を通る。

### 13.16 依頼テンプレートの共通契約

`templates/diagnose-template.txt` と `templates/repair-template.txt` は、依頼を作るたび
strict UTF-8 で読み直す。欠落、読取不可、不正 UTF-8、変数違反は E-GEN-02 で中止し、
内蔵文面へ fallback しない。段階固有の必須変数は §4.2 と §5.3 が定める。

| 共通変数 | 差し込む値 |
|---|---|
| `{{REQUEST_TEXT}}` | ひな形の `## 改修指示` と、その段階で利用者が加えた文 |
| `{{OUTPUT_RULES}}` | 選んだ出力指示。分割を選んだときは対応する分割用の節 |
| `{{BOOK_NAME}}` | ディレクトリを含まない元ブック名 |
| `{{MODULE_COUNT}}` / `{{TOTAL_LINE_COUNT}}` | 読み取ったモジュール数 / 合計行数 |
| `{{MODULE_LIST}}` | `- 名前（種別, 行数）` の全モジュール一覧 |
| `{{CODE_FILE_NAME}}` | 固定名 `source-code.md` |
| `{{REQUEST_ID}}` | その段階で発行した UUID v4 |

- 既知変数は複数回使える。未知の `{{NAME}}`、壊れた変数表記、旧
  `{{MODULE_SOURCE_BLOCKS}}` は E-GEN-02。値の中にある `{{NAME}}` は再解釈しない。
- 値は内容を解釈・escape・代替せず、改行だけ CRLF へ正規化する。値末尾と
  テンプレート直後の改行は重複分を重ね合わせ、段落境界を保つ。
- テンプレートは中立な枠だけを持つ。改修指示、返答形式、最小変更などの文面は
  ひな形の節が唯一の正本であり、テンプレートや製品コードへ複製しない。

### 13.17 host bridge、IPC、クリップボード

`host-bridge.js` は id 付き request を送り、`MessageRouter` が同じ id の success / error
で Promise を解決する。信頼 origin の検査は JSON を読む前に行う（§13.12.1）。
`attachBook` と `buildBook` は UI thread を塞がない engine action、ほかは STA 上で処理する。

| action | 役割 |
|---|---|
| `getAppInfo` | 版、診断/改修の preset 2 群、環境ファイルの有無 |
| `getTargetEnvironment` | JSON を strict UTF-8 で読み、未解釈の `content` を返す |
| `pickBook` / `resolveDroppedFiles` / `attachBook` | 選択・drop の実パス解決・VBA 読み取り |
| `readPreset` / `readRequestTemplate` | containment 検査後の strict UTF-8 読み取り |
| `writeRequestFiles` | 診断段階のフォルダ・コード・依頼、または改修依頼の原子的書き出し |
| `writeDiagnosisFile` | 受理した診断の記録を原子的に書き出す |
| `writeClipboard` / `readClipboard` | 文字列のコピー / 読み取り（§8.5 の有界再試行） |
| `buildBook` | 変更・追加、出力名、diff、result を受けて別名ブックを構築・再検証 |
| `revealPath` / `writeLog` | Explorer で場所を開く / 値を含めない運用ログ |

依頼文のコピーは C# の `Clipboard.SetText`、返答のボタン取り込みは `GetText` を使う。
取り込み欄の Ctrl+V は DOM の `paste` event から同じ parser へ入る第 2 経路であり、
ブラウザ permission を要求しない。いずれも同じ状態遷移・検証を通り、空文字と
OS 例外を混同しない。

### 13.18 モジュールの状態

「全モジュールがそのままで始まり、受理した改修パッケージに名乗られたものだけが
書き戻し候補になる」を基本とする。

| 状態 | 一覧 | 決める事実 |
|---|---|---|
| 未取り込み | 灰 + そのまま | 初期状態、または現在のパッケージに無い |
| 変更あり | 青 + `+N 行` | 受理した全文がブックの可視コードと違う |
| 変更なし | 灰 + 変更なし | 受理した全文が現在コードと同一 |
| 変更あり（新規） | 青 + 新規 | 受理した standard モジュールがブックに無い |

- 取り込み直しは追加でなく**置き換え**である。検証済みの新パッケージを適用する前に
  前回分を外し、前回だけの変更を未取り込みへ、前回だけの新規を一覧外へ戻す。
- 判定は常にブック由来のモジュールに対して行う。前回追加した新規を既存扱いしない。
- 単位はパッケージ 1 つで、モジュールごとの採否は持たない。分割受理中の part は
  部品であり、全件統合・全体検証が済むまでモジュール状態を動かさない。
- 取り込みは `intakeRequestId` で現行改修依頼へ結び付ける。古い依頼の結果、
  `UNNECESSARY` / `IMPOSSIBLE` / `UNCLEAR` は diff・ビルドへ進めない。
- 決定的置換は同じ staged module 形式を作り、画面 7 以降は AI 経路と区別しない。
- **前回分を外す対象は「AI の返答」であって「このツールが行った置換」ではない。**
  両方の経路では、返答を捨てたあとに置換結果のコードを復元してから新しい返答を
  重ねる（§7.2）。返答が名乗らなかったモジュールは置換済みのまま残る。

### 13.19 出力、完了、世代交換

- 画面 7 で変更と diff、画面 8 で出力名と作成予定ファイル、画面 9 でビルド中、
  画面 10 で結果を表示する。ビルド中は戻る・次へ・再実行を無効にする。
- 改修済みブック名はファイル名だけを受け付け、元と同じ拡張子を要求する。区切り文字、
  `..`、実行フォルダ外へ出る値を UI と host の両方で拒否する。
- 元ブックは上書きしない。差分 HTML には変更しなかったモジュールも載せ、1 ファイルで
  改修前後の全 VBA を確認できるようにする。`result.md` は AI の SUMMARY と機械的な
  ビルド結果を記録し、コード本文を複製しない。
- ビルド後も戻って入力・取り込みを直し、同じ実行フォルダへ再ビルドできる。
  置き換えるのは**このアプリがこの実行で作った成果物だけ**。同名でも所有していない
  ファイルは E-BUILD-03 で止める。
- 改修済みブックは作業名で構築し、§14.1 の再読検証に合格してから本来の名前へ
  差し替える。失敗した世代は前の正常世代を壊さず、作業ファイルも残さない。
- 差分 HTML または `result.md` だけの書き出し失敗は完了画面とログへ個別に出す。
  検証済みブックの成功を取り消さない一方、片方の失敗を黙らせない。

#### 13.19.1 VBA のコード署名は出力に残さない（SIG-01）

出力は元ファイルの複製に `vbaProject.bin` だけを差し替えたものである。
**署名は VBA プロジェクトに対して付いている**ので、そのまま複製されると
「署名対象は書き換わったのに署名だけ残っている」状態になる。
「署名がある」は利用者が**実行してよいと判断する根拠**なので、
不整合な署名を残すのは署名が無いより悪い。

したがってビルドは、**署名部品を出力から取り除く**:

| 取り除くもの | 例 |
|---|---|
| 署名部品そのもの | `xl/vbaProjectSignature.bin` / `…SignatureAgile.bin` / `…SignatureV3.bin` |
| それを指す関連付け | `xl/_rels/vbaProject.bin.rels` の該当 `<Relationship>`。残りが 0 本ならこの部品ごと削除 |
| コンテンツタイプの宣言 | `[Content_Types].xml` の該当 `<Override>` |

部品名の判定は `vbaprojectsignature` を含むかどうか（大小無視）で、
`09_BookInventory.cs` の検知と同じ規則を使う。

**`.bin` だけを消してはならない。** 存在しない部品を指す関連付けが残ると
パッケージとして壊れ、壊れた署名の代わりに**開けないブック**を出すことになる。

伝え方も契約に含める:

- **添付時**（画面 0）に署名を検知したら、その場で
  「改修済みブックからは署名を外すので、配布前に署名し直すこと」を出す。
  折りたたみの中だけに置かない（閉じた一覧は警告にならない）
- **完了時**（画面 10）に、この出力に署名が付いていないことと再署名の必要を出す

**署名の無いブックはこの経路を一切通らない。** 部品が 1 つも無ければ
関連付けもコンテンツタイプも読み書きせず、出力は従来どおり
`vbaProject.bin` 以外バイト単位で元のままになる。

### 13.20 既存エラーの契約

エラーで状態を壊さず、直前の画面に留まり、元ブックを無傷に保つ。利用者向けには
「何が起きたか + 次にどうするか」を出し、技術詳細と stack はログへ送る。
β2.00 で追加した ID は §8.3 に定める。

| ID | 事象 | 挙動 |
|---|---|---|
| `E-ATTACH-02` | 消失・権限などでファイルを読めない | 場所とアクセス権を案内 |
| `E-ATTACH-03` | どの経路でも VBA が無い | ブック選択を保ち、マクロ無しをカード表示 |
| `E-ATTACH-04` | ファイル全体が暗号化 | 診断材料を作らず、パスワードを外したコピーを案内 |
| `E-GEN-01` | 実行フォルダまたは段階成果物の原子的書き出し失敗 | 状態不変。権限・空き容量を案内 |
| `E-GEN-02` | template の欠落・不正 UTF-8・変数違反 | fallback せず依頼生成を中止 |
| `E-GEN-03` | 依頼文のコピー失敗 | ファイルは保持し、［もう一度コピー］を案内 |
| `E-INTAKE-01` | 改修返答が §13.9 / §13.10 に不合格 | 何も取り込まず、コードブロック全体の再コピーを案内 |
| `E-PASTE-01` | 空、または §13.13 後に空 | 手動修正を反映せず入力を確認させる |
| `E-PRESET-01` | 改修ひな形の書式不正 | 現行選択・依頼を保ち、該当ファイルを案内 |
| `E-BUILD-01` | 再構築を含む内部エラー | 出力を破棄し、元ブックと前世代を保持 |
| `E-BUILD-02` | 読み直し検証の不一致 | 安全のため出力を破棄 |
| `E-BUILD-03` | 出力先・出力名・非所有の同名ファイル | 非所有ファイルを触らず停止 |
| `E-BUILD-04` | 添付時とビルド直前の VBA が不一致 | 出力前に停止し、読み込み直しを案内 |
| `E-SYS-01` | WebView2 Runtime 無し | UI 起動前に native MessageBox で導入を案内 |
| `E-SYS-02` | host bridge / その他の未捕捉例外 | 状態を保ちトースト + ログ |

**`E-ATTACH-02` / `-03` / `-04` は、すでに読み込み済みのブックを捨てない。**
拒否されたファイルは 1 バイトも読まれていないので、この実行の対象は
**直前に読み込んだブックのまま**であり、［次へ］もそのブックに対して有効なままである。
これは正しい状態だが、赤いカードの下で［次へ］が押せる画面は
「失敗したのに進める」と読めるため、**カードに「読み込み済みのブックは
◯◯ のままです。このまま次へ進めます。」を明示する**（`inline-error-kept`）。

［次へ］を機械的に無効化しない。すでに諦めたファイルのせいで、
関係のない作業まで止めることになるためである。
拒否をきっかけに前のブックを破棄することもしない。選び間違い 1 回で
実際の作業を捨てることになり、拒否の代償として重すぎる。

## 14. ビルド仕様（書き戻しエンジン）

### 14.1 手順

0. **添付時点との同一性を確認する**。添付（`attachBook`）で読んだ VBA project を
   内容署名（全モジュールの名前・種類・コード長・コード本文を、コードに現れない
   区切りで連結したテキスト）として host が保持する。ビルドは自分で読み直した
   project から同じ署名を作り、保持しているものと**完全一致**でなければ
   E-BUILD-04 で中止する。ファイルは 1 度だけ読み、比較はハッシュではなく
   正規化テキストの一致で行う。
   - 中止は出力を作る前に起こるので、生成物は一切残らない。
   - 目的は「AI へ渡したコードを基にした返答を、その後で保存された元ブックへ
     上書きして、後からの手修正を黙って失う」経路を閉じることである。
     添付後に Excel でブックを編集・保存した場合は、読み込み直して依頼を
     作り直す必要がある。
   - 判定対象は VBA project の内容だけである。シートのセルなど VBA 以外の変更で
     ビルドを止めることはしない（生成ブックはその時点の元ブックのコピーであり、
     VBA だけを差し替える）。
1. 元ブックを出力名（§8.1）でコピーする。**元ファイルには一切触れない**。
   同じ実行が既に作ったブックを置き換える再ビルドでは、同じフォルダの作業名へ
   コピーし、検証に合格した後で本来の名前へ差し替える（§8.1）。
2. コピーから vbaProject.bin（zip エントリ）を取り出し、OLE2 として読み込み、
   **全エントリの論理情報と全ストリーム内容をメモリに展開**する。
3. 書き戻し対象モジュール（取り込み済みかつ変更あり）ごとに、新しいストリーム内容を作る:
   - 既存モジュールは、最終コード（Attribute 付き）をプロジェクトのコードページで
     encode → MS-OVBA 圧縮する。モジュールストリームの先頭
     `[0, SourceOffset)`（PerformanceCache 部）は
     そのまま温存し、`SourceOffset` 以降を新しい圧縮データに差し替える。
     **SourceOffset は dir の MODULEOFFSET を正本**とし、書き戻し対象ストリームは
     **dir の MODULESTREAMNAME で対応付ける**。
   - 新規標準モジュールは `Attribute VB_Name` と可視コードの全文を圧縮し、
     PerformanceCache なし（`MODULEOFFSET=0`）の新規ストリームにする。
     dir の `PROJECTMODULES` と MODULE レコード、PROJECT の `Module=` 行、
     PROJECTwm の NAMEMAP を同じ順序で追加する。
4. **OLE2 複合ドキュメントを丸ごと再構築する（§14.2。唯一の書き込み経路）**:
   全エントリ（差し替えたストリームと新規モジュールストリームを含む）を
   新しいコンテナとして直列化する。
5. 再構築した vbaProject.bin をコピー先ブックに書き戻す（zip の該当エントリを
   Update モードで書き換え）。
6. **検証（必須手順）**: コピー先ブックをエンジンで読み直し、次の 3 点を確認する。
   - (a) 書き戻した全モジュールの展開後テキストが、渡した最終コードと一致
     （CRLF 正規化後の完全一致）
   - (b) 新規追加時に更新する dir / PROJECT / PROJECTwm と新規ストリームを除き、
     **それ以外の全ストリームが元の内容と byte 単位で一致**
   - (c) ストレージ/ストリームの木構造・名前・種別・CLSID・state bits が
     維持されている
7. 1 つでも失敗（検証・I/O）したら**出力ファイルを削除**し、モジュール別の結果を
   返す（**all-or-nothing**。中途半端に直ったブックを現場に残さない）。

### 14.2 全面再構築方式

**なぜ全面再構築か**: 既存セクタチェーンへ in-place で書き込む方式
（+ パディング + リロケートの 3 段配置規則）は、本ツールの用途では成立しない。
実測では、典型的な改修として 1 行追加しただけで、検証した全モジュール
（18/18。すべて mini ストリーム、スラック 0〜41B に対し圧縮後の増分 55〜75B）が
in-place 不能だった。「コードが増える」のが常態である以上、
**全面再構築を唯一の書き込み経路**とする。

**方式**: コンテナ（MS-CFB）水準の再構築。

- **保持する論理情報**（元から機械的に移送）: ストレージ/ストリームの木構造（親子）、
  名前、種別、CLSID、state bits、作成/更新時刻、全ストリーム内容。
  モジュールストリーム以外のストリーム（`_VBA_PROJECT` / `dir` / `__SRP_*` /
  `PROJECT` / `PROJECTwm` 等）は、既存モジュールだけの変更では
  **内容を解釈せず、不透明な byte 列としてコピー**する。新規追加時だけ、
  dir / PROJECT / PROJECTwm に規定のレコードを追加する。
- **毎回新規に決めるもの**（物理配置。MS-CFB 上、意味を持たない）: セクタ番号、
  チェーン順序、空きセクタ、FAT / DIFAT / miniFAT の中身。
- mini / 通常ストリームの所属は、再構築時に各ストリームのサイズ（cutoff 4096）から
  自然に決まる。**パディングは不要**。
- ディレクトリの兄弟赤黒木は MS-CFB の名前順（長さ → 大文字化比較）で構築する。
- 出力は v3（512B セクタ）で直列化する。v4（4096B セクタ）の入力は実務上ほぼ無い
  想定で、遭遇した場合は明示エラーにする（未検証事項として記録）。
- 出力ファイルのバイト配置は元と変わる（空きセクタが落ちるため通常は小さくなる）が、
  意味的な差はない。
- 署名: VBA プロジェクト署名は vbaProject.bin の外の別パート
  （`xl/vbaProjectSignature.bin` 等）にあり、モジュールを書き換えた時点でどの書き込み
  方式でも無効になる。再構築固有の不利ではない。v1 は署名パートに触れない。

**品質保証（必須。すべて満たすまでリリースしない）**:

1. **ラウンドトリップ試験**: 無変更で再構築 → 全ストリーム byte 一致・木構造等の
   論理情報一致（開発時の常設テスト。毎ビルドが同じ経路を通るため、この試験が
   本番経路そのものを検証する）。
2. **ビルド後の読み直し検証**（§14.1-6。全ストリーム対象）。
3. **Excel 実機確認**（再構築した出力を Excel で開き、マクロ動作を確認する。
   リリース前の手動確認項目）。

### 14.3 書き戻しが変更しないもの

- 既存モジュールの PerformanceCache（各モジュールストリームの先頭部）、
  `_VBA_PROJECT` / `__SRP_*` 等の他ストリーム: **内容を一切変更しない**
  （再構築で物理配置は変わるが、内容は byte 単位で維持され、§14.1-6(b) で検証される）。
  既存ソースの差し替えと新規標準モジュールの追加だけを行い、再コンパイルは Excel 側に任せる。
- dir / PROJECT / PROJECTwm は新規追加時だけ必要なレコードを追記し、
  それ以外の既存 byte 列を維持する。
- zip 内の vbaProject.bin 以外のエントリ（シートデータ等）: 触れない。

### 14.4 モジュール別結果コード

| result | 意味 | all-or-nothing 後の扱い |
|---|---|---|
| `written` | 書き戻し・検証 OK | 成功時のみ |
| `verify_failed` | 読み直し検証で不一致 | 全体失敗（出力破棄） |
| `io_error` | コピー/zip 書き戻し失敗 | 全体失敗 |
| `skipped_no_change` | 変更なしのため書き戻し対象外 | 情報表示のみ |

再構築処理そのものの内部エラーは、モジュール別ではなくビルド全体のエラーとして
扱う（E-BUILD-01。出力は残さない）。添付時点との不一致（§14.1-0）も
モジュール別ではなくビルド全体のエラー（E-BUILD-04）とし、出力を作らない。

### 15.2 未検証・限定的な範囲

1. **v4（4096B セクタ）の CFB 入力**: 読み取りは可能だが、書き出しは v3 のみ。
   v4 入力の再構築要求は明示エラーになる。実ファイルでの遭遇例は未確認。
2. **起動時ネイティブエラーのログ副作用**: WebView2 ランタイム不在時の MessageBox 経路は
   実機確認済み。その後に追加した起動エラーの best-effort ログ出力は、コンパイル確認
   のみで、ランタイム不在を再現しての実測はしていない。
3. **配布形態の E2E**: 別ディレクトリへ配置した状態からの `launch.vbs` 起動・ウィンドウ表示・
   コンソール非表示・ログ出力・終了は実プロセスで確認済み。ただしステップ ①〜④ の
   通し確認は、同じ配置物から起動した検証用 harness で行っており、先に起動した
   実プロセスを UI 自動操作したものではない。
4. **モジュール単位出力（§13.10）の実チャット**: 区切り行の解析・複数回の受け取り・
   統合・拒否・生成される依頼文・チェックボックスの実操作は、ヘッドレステストと
   WebView2 実動テスト（`tests\test-split-webview.ps1`）で確認済み。実際のチャット AI が
   `PART` 行と 1 返答 1 モジュールをどこまで守るかは、実運用での確認が必要。
5. **120 秒を超えるビルド（§13.12.3）**: 遅延応答の解決と「時間がかかっています」の
   表示は host bridge のテストで確認済み。実際に 120 秒を超える大容量ブックでの
   実測は未実施。
6. **E-BUILD-04（§14.1-0）**: 添付後に元ブックの VBA を差し替えたヘッドレス再現で
   確認済み。Excel で開いたまま編集・保存した実操作での再現は未実施。
7. **読み取り結果の切り分け（§13.6）**: 正常ブック（`clean`）、EOCD を壊した
   ブック（`structureOnly` + 容器経路）、vbaProject.bin を切り詰めたブック
   （`sourceDoubt`）の 3 通りを実ファイルで確認済み。best-effort 展開だけが
   起きる（ストリームは短くない）ケースの実ファイルは用意できておらず、
   そこでモジュール名が列挙されることは合成データでの確認にとどまる。
8. **差分 HTML の閲覧環境（§13.11）**: 生成した実ファイルを WebView2（Chromium）で
   開き、前／次の変更・変更箇所のみ・折り返し・ライト／ダーク・モジュール切替を
   実クリックで確認済み。Firefox / Safari など他エンジンでの表示は未確認。
   また `file://` で直接開いた場合の `localStorage`（テーマの記憶）は環境により
   使えないことがあり、その場合もテーマ切替はそのページの中では動く。
9. **出力名の日付（§8.1）**: ブックを読み込んだ日と実際にビルドした日が異なる
   セッション（日付をまたぐ作業）では、名前に付く日付は読み込んだ日のままになる。
   1 つの実行で名前が食い違わないことを優先した結果であり、実測はしていない。
10. **WebView2 の境界（§13.12.1）**: 遷移・新窓・frame・別 origin からのメッセージの
   拒否と設定は、実動する窓で結果を見て確認済み（`tests\test-webview-security.ps1`）。
   起動時に `about:blank` 等の遷移が要求されないことは同梱ランタイム

   限らない。要求されるようになった場合は製品ページが読めなくなるため、
   黙って通ることはない。`AreBrowserAcceleratorKeysEnabled = false` でも
   Ctrl+V の貼り付けが効くことは実キー入力で確認済みだが、それ以外の編集キーは
   個別に確認していない。
