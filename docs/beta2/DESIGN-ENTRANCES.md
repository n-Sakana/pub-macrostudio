# MacroStudio β2.00 設計 — 入口を3つに分ける

2026-08-03。先生との壁打ちで確定した設計。

**版は β2.00 のままである。** 機能が増えても版は上げない。本書は
[README.md](README.md) が挙げる β2.00 の設計文書の 5 冊目で、入口を 3 つに
分けた回の記録である。

**実装済み（2026-08-04）。** 本文の契約は `docs/SPEC.md` §2・§4 へ取り込んだ。
そちらが正本で、本書は経緯の記録である。node 53 本と PowerShell 33 本が通り、
3 つの入口はすべて実 WebView2 で通した（`tests\test-flow-webview.ps1` が
マクロ改修、`tests\test-entrance-routes.ps1` がリファクタとフリー依頼）。

---

## 1. なぜ

この版は当初、入口を1本にした。用途を選ばせず、ブックを読み、診断し、直す。
そのとき解いていたのは「β1.10 の3入口（AIで改修／AIで相談／簡易モード）が、
同じ作業への3つの言い方になっていて、選ぶ意味が無かった」という問題である。

ここで解くのは別の問題である。

> 初心者がただマクロを動くようにしたいだけなのに、高速化やエラー処理が
> ブロッカー扱いされてたらうっとおしい。

当初の診断は「対象環境で起きる事実」を1本で監査していた。そこへ「遅い」「壊れやすい」
が混ざると、**動かすことだけが目的の読者に、動くものの話が阻害として出る。**
これは入口が1本であることの帰結であって、診断の書き方で回避できない。

したがってここでは、β1.10 の3入口を戻すのではなく、**スコープの違う3つの作業を
分ける**。同じ作業への言い方を増やすことはしない。

## 2. 入口

ブックを読む前に、最初の画面で3つから選ぶ。

| 入口 | 何をする | 診断 |
|---|---|---|
| **マクロ改修** | 動かないものを動くようにする | 動くかどうかを監査 |
| **リファクタ** | 動いているものを良くする | 直す価値を採点 |
| **フリー依頼** | 言われたことをやる | なし |

スコープが分かれるのは**診断そのもの**である。画面での絞り込みでも、ひな形の
絞り込みでもない。AI は最初から1つのスコープしか見ない。したがってマクロ改修の
診断に「セル逐次ループが遅い」は**原理的に出てこない**。

### 2.1 入口が診断の範囲を決める

| 入口 | 「問題である」の定義 | 手引書の対応箇所 |
|---|---|---|
| マクロ改修 | 動かない。コンパイルエラー、実行時に落ちる、明らかに不合理な動作 | §2-C 上4項目、§3.1、§3.2 |
| リファクタ | 直す価値がある | §2-C 下2項目、§3.1 推奨改修 4-5、§4 Step 4 |
| フリー依頼 | 利用者が書いたこと | 手引書の外 |

手引書 §2-C「改修」の8項目を、**MacroStudio が VBA のソーステキストしか
書き換えられない**という事実で割ると、この3つに分かれる。

| 手引書 §2-C の項目 | ソースで片が付くか | 動くか | 行き先 |
|---|---|---|---|
| パスを設定値へ置換 | ✓ | 動かない | マクロ改修 |
| URL とローカルパスを同一視した処理を分離 | ✓ | 動かない | マクロ改修 |
| Win32 API を標準機能へ置換 | ✓ | 動かない | マクロ改修 |
| 64bit 対応が必要な API 宣言を精査 | ✓ | 動かない | マクロ改修 |
| Power Query の接続先と認証方式を再設定 | ✗ | 動かない | 引渡しメモ（人） |
| バーコード生成方式を変更 | ✗ | 動かない | 引渡しメモ（人） |
| 不要な宣言・デッドコードを削除 | ✓ | 動く | リファクタ |
| 例外処理、ログ出力、入力値検証を追加または見直す | ✓ | 動く | リファクタ |

参照設定・Power Query の接続・ActiveX・フォント・署名・信頼設定は、
MacroStudio が読めても書けない。これらは**入口によらず常に「人がやること」**
として棚卸しから引渡しメモへ出る（`handover.js` が既に行っている）。

## 3. 判定

両入口とも A〜D。**A が良く D が悪い**で単調にする。

### 3.1 マクロ改修

事実の判定であり、裁量が無い。

| | 意味 |
|---|---|
| **A** | 動作に支障なし |
| **B** | **要改修** — 動かない／このツールで直せる |
| **C** | **不明** — 動かない／このツールでは直せない。人が環境側で手を打つ余地はある |
| **D** | **改修不可** — 動かない／置き換え先が存在しないことが確定している |

C と D を分ける理由は、**その先に道があるかどうか**である。C は環境側の手配
（参照設定を入れる、接続先を変える、ActiveX を有効化する）で解決し得る。
D は解決し得ない。Win32 API が使えない環境でウィンドウハンドルを操作している
処理は、VBA 標準に等価物が無いので、ソースをどう書き換えても実現できない。
利用者が次にすることが全く違う（C は環境側の手配、D は作り直しの判断）。

**D は診断が言える中で最も重い結論なので、名乗る条件を締める。**

- 何がどの標準機能で置き換えられないのかを根拠として必ず書く
- `CONFIDENCE=CONFIRMED` でなければ D を名乗れない。「たぶん無理」は C
- 画面では D を最上位に出す。B が10件あっても D が1件あれば先に読むのは D

**依頼に入るのは B だけ。** C と D は依頼に入らない。入れても直せない。
C と D は「人がやること」として引渡しメモへ合流する。

### 3.2 リファクタ

**AI の裁量による定性判断**である。定量に見せかけない。

| | 意味 |
|---|---|
| **A** | リファクタする価値は見当たらない |
| **B** | 少しある |
| **C** | ある |
| **D** | 大きい |

- ブック全体で **1つ**。基準ごと・観点ごとの採点はしない
- 理由は散文。章立ても AI が決める
- 個別の行番号は挙げない（メモ「個別の個所の指摘をだらだら書くのではなく、
  整理して出力する」）
- 画面に「これは AI の見立てです。同じコードでも AI によって変わります」と書く

**採点の基準はひな形が持つ。** `VBAリファクター` の `## 改修指示` が基準であり、
診断ひな形は基準を持たない。速さ／壊れにくさ／読みやすさのような軸を
アプリや診断ひな形が作らない。理由は2つある。

1. 抽象軸に文字を付けると、比べられないものを比べさせる。「速さ D／
   壊れにくさ C」は「速さの方が悪い」と読まれるが、その比較には意味が無い
2. 改修指示の文面を複製しない、というこのリポジトリの規約
   （`tests\test-preset-migration.js` が門番）

基準は `{{GRADING_BASIS}}` で診断依頼へ差し込む（§6.3）。

### 3.3 二つの判定は性質が違う。画面で隠さない

| | マクロ改修 | リファクタ |
|---|---|---|
| 質問 | 動くか | 直す価値があるか |
| 判定 | 事実。裁量なし | AI の見立て |
| 単位 | 指摘ごと | ブック全体で1つ |
| 出すもの | 指摘の一覧 | 理由の散文 |
| 「AI の見立てです」の断り | 書かない | **書く** |

マクロ改修側に断りを書くと嘘になる。リファクタ側に書かないと嘘になる。

## 4. ワークフロー

### 4.1 画面（11枠）

```
                        マクロ改修   リファクタ   フリー依頼
0  entrance   何をするか    ●           ●           ●     ← 新規
1  book       ブックを読む  ●           ●           ●
2  diagnose   受け渡し      ●           ●           ─
3  result     A〜D          ●           ●           ─
4  nextStep   ひな形        ●           ─           ─
5  repairInput 内容        指摘を選ぶ  備考のみ    自分で書く
6  repair     受け渡し      ●           ●           ●
7  review     差分          ●           ●           ●
8  output     出力名        ●           ●           ●
9  build      ビルド        ●           ●           ●
10 done       完了          ●           ●           ●
```

実際に歩くのは **マクロ改修 8／リファクタ 8／フリー依頼 7**。

### 4.2 画面4を出す条件

> **その入口の改修ひな形が2つ以上あるときだけ出す。**

| 入口 | 改修ひな形 | 画面4 |
|---|---|---|
| マクロ改修 | 4つ | 出る |
| リファクタ | 1つ | 飛ばす |
| フリー依頼 | 1つ | 飛ばす |

入口ごとの例外規則を書かない。将来リファクタのひな形が2つになれば自動的に出る。

### 4.3 上部の4段階

手引書の工程に合わせる。

```
① 決めて読む      ② 診断する      ③ 改修する      ④ 作って引き渡す
   §2-A 事前保全     §2-B 判定       §2-C 改修       §2-E 引渡し
   §4 Step 1         §4 Step 2-3     §4 Step 4       §4 Step 6
```

§2-D テスト（§4 Step 5）はツールの外にある。引渡しメモが §5 の4区分を
未実施として出す（`handover.js` が既に行っている）。

### 4.4 消えるもの

- 診断画面の**「診断を飛ばして、直したいことを自分で書く」チェックボックス**。
  フリー依頼が入口としてそれになる。隠れた分岐が表に出る
- 診断結果画面の「要改修／要確認／改修不要」の3箱（A〜D が置き換える）

### 4.5 足すもの

画面1に手引書 §2-A の1行を出す。

> 改修前に、いまの環境で正常に動いた結果を保存しておいてください。
> 改修後に何が変わったかを比べる基準になります。

手引書は事前保全を**最初の工程**に置いている。完了画面のメモで言っても遅い。

### 4.6 入口を選び直す

画面0へ戻れる。入口が変わればブック以降の状態は捨てる（既存の
`invalidateDiagnosisResult` 系の経路に乗せる）。ブックは読み直さない。

## 5. ひな形の構成

「段階はフォルダで決まる」という既存の規約を、入口へ一段伸ばす。

```
presets/
  01_マクロ改修/
    01_診断/  01_動くかどうかの監査.md
    02_改修/  01_Win32 API を使わない形へ直す.md
              02_固定パスを新環境へ置き換える.md
              03_OSや外部プログラムへの依存を減らす.md
              04_新しい保存先で成り立つファイル操作へ直す.md
              05_診断で見つかった故障を直す.md          ← 新規
  02_リファクタ/
    01_診断/  01_リファクタの価値を採点する.md
    02_改修/  01_VBAリファクター.md
  03_フリー依頼/
    02_改修/  01_自分で改修内容を書く.md
```

`05_診断で見つかった故障を直す.md` を足す理由。**B（要改修）に入った指摘は、
必ずどれかのひな形が受け持てなければならない。** 環境由来でない単純な故障
（シート名の綴り違い、初期化していない変数、必ず落ちる分岐）は環境キーを
持たないので、上の4つはどれも名乗れない。受け皿が無いと、B と表示しておいて
依頼を作れないという空振りが起きる。

このひな形は `## 推奨条件` を持たない（★推奨は付かない）。選んだ指摘そのものが
依頼になる、という既存の形をそのまま使う。「自分で改修内容を書く」との違いは、
**利用者が書かなくてよい**ことである。

**規則:** 選んだ入口の `01_診断/` に有効なファイルがちょうど1つ。
0 件または2件以上は `E-PRESET-02`。`01_診断/` を持たない入口は診断しない。
既存の cardinality 規則を入口ごとに適用するだけで、新しい規則を作らない。

### 5.1 備考欄

新しい機構を作らない。既存の `## 記入欄` を使う。ひな形が欄の名前を決め、
書かれた本文は依頼文の【追加の要望】へ入る。

| 入口 | 欄の名前 | 既定 |
|---|---|---|
| マクロ改修 | 追加の要望 | 畳む（任意） |
| リファクタ | 例外事情・触ってほしくない箇所 | 畳む（任意） |
| フリー依頼 | 改修してほしい内容 | 開く（必須） |

## 6. 診断契約

### 6.1 CLASS を GRADE に置き換える

META のキー数は変わらない。

```
旧  META CLASS=BLOCKER    CONFIDENCE=CONFIRMED MODULE=… PROC=… LINES=… ENVKEY=…
新  META GRADE=B          CONFIDENCE=CONFIRMED MODULE=… PROC=… LINES=… ENVKEY=…
```

`BLOCKER` / `DEFECT` / `CONDITIONAL` / `EXTERNAL` / `INFO` は A〜D が
包含する。2つ持つと同じことを2回言うことになる。

- `GRADE=D` は `CONFIDENCE=CONFIRMED` を要求する（§3.1）
- `ENVKEY` は残す。`-` を許す。**環境由来でない故障が名乗れるようになる**
- 同じ環境キーの指摘を1つの問題へまとめる既存の集約はそのまま
- `ENVKEY=-` の指摘は、`TITLE` の1行目で束ねる（既存の fallback と同じ）

### 6.2 診断は2形ある

入口によって返る形が違う。**どちらの形かは診断ひな形が宣言する。**

**指摘型**（マクロ改修）

```
DIAG BEGIN <件数>
SECTION PURPOSE …／FLOW …／DEPENDENCY …／ENVIRONMENT …
FINDING <n> GRADE=… CONFIDENCE=… MODULE=… PROC=… LINES=… ENVKEY=…
TITLE: …／CONDITION: …／IMPACT: …／EVIDENCE: …
DIAG COMPLETE <件数>
DIAG END
```

**採点型**（リファクタ）

```
DIAG BEGIN 0
SECTION PURPOSE …／FLOW …／DEPENDENCY …
DIAG GRADE <A-D>
SECTION REASON （理由の散文。複数行可）
DIAG COMPLETE 0
DIAG END
```

節の名前が固定で `diagnosis-package.js` に書いてあるのを、**ひな形が宣言する
形へ移す**。`## 返す節` と `## 返す形`（指摘型／採点型）を診断ひな形が持ち、
`preset-document.js` が読み、`parse(text, {sections, shape, …})` へ渡す。
`detect(modules, rules)` が規則を渡される形と同じ扱いで、アプリは節の意味を
知らない。

形によって変わる検査。

| 検査 | 指摘型 | 採点型 |
|---|---|---|
| 節がちょうど1回ずつ、本文付きで揃う（D04） | 宣言された節 | 宣言された節 |
| 0 件のとき `DIAG NOFINDING <理由>` が1行（D20） | **要る** | **要らない**（常に0件なので） |
| `DIAG GRADE <A-D>` がちょうど1行 | 無いこと | **要る** |
| `FINDING` の `GRADE` | 要る | FINDING を書かない |

採点型で `DIAG NOFINDING` を求めると、毎回「指摘0件の理由」を書かせることに
なる。採点型は指摘を出さない形なので、0 件は結論ではなく前提である。

`ENVIRONMENT` 節はマクロ改修だけが持つ（対象環境で何が起きるかを言う節なので）。
リファクタは `PURPOSE` / `FLOW` / `DEPENDENCY` / `REASON` の4節。
画面の「このマクロの詳細」は、宣言された節をそのまま並べる。

### 6.3 `{{GRADING_BASIS}}`

`templates/diagnose-template.txt` に差し込み変数を1つ足す。

```
【想定動作環境】   {{TARGET_ENVIRONMENT}}
{{OUTSIDE_CODE}}【診断指示】       {{REQUEST_TEXT}}
【改修の基準】     {{GRADING_BASIS}}
【対象モジュール】 {{MODULE_LIST}}
{{OUTPUT_RULES}}
```

**その入口の改修ひな形がちょうど1つのときだけ**、その `## 改修指示` が入る。
アプリは中身を読まない。基準を書き換えたければひな形1か所を直せば、
診断と改修が同時に変わる。マクロ改修の診断ひな形はこの変数を使わない
（基準が「動くか」で、ひな形を要しない）。

### 6.4 マクロ改修の診断ひな形へ、手引書から足すもの

いまの `01_動作環境の事実監査.md` を拡張する。すべて手引書が持っている内容で、
アプリ側には書かない。

- **§4 Step 2 の検索対象**を列挙する。
  `\\` `:\` `.Path` `.FullName` ／ `Dir` `Open` `Kill` `FileCopy`
  `FileSystemObject` ／ `Declare` `Lib` `PtrSafe` ／ `Shell` `WScript.Shell`
  `Shell.Application` ／ `ConnectionString` `Provider=` `OLEDB` `ODBC` ／
  `.Run` `.Exec`
- **§3.1 の留意点5つ**（カレントディレクトリが存在する／相対パスで常に同じ
  ファイルを参照できる／URL を直接渡せる／属性を同様に取得できる／排他制御なしで
  上書きできる）を、動くかどうかの判定材料として
- **§4 Step 3 の5問**（どの入力を受けるか／どの依存か／どこから呼ばれるか／
  失敗時にどの状態が残るか／代替に変えたときの業務影響）
- **環境由来でない故障**（コンパイルエラー、明らかに不合理な動作）も対象
- A〜D の判定と、その根拠

手引書 §4 Step 2 は出力形式まで書いている。

> 検索結果は、該当モジュール、プロシージャ、行、用途、改修要否で一覧化します。

`MODULE` `PROC` `LINES` と TEXT、そして `GRADE` がこれに対応する。
診断契約は手引書の指示そのものである。

### 6.5 リファクタの診断ひな形（新規）

基準を持たない。言うのはこれだけ。

> 添付したコードを読み、下の【改修の基準】に照らして、このコードに
> リファクタの価値がどれだけあるかを A〜D で1つ付けてください。
> そう判断した理由を、基準のどれに当たるかが分かるように書いてください。
> 個別の行番号は挙げないでください。

### 6.6 リファクタの改修ひな形の変更

`VBAリファクター` の進め方 2「次に選ぶ」を、診断が既に行っている。
改修指示に1文足す。

> 診断で D または C と判断された基準を優先してください。
> A または B と判断された基準には触れないでください。

これで診断の A〜D が第2 AI への指示になる。**B（直せるが直さない方がよい）が
実際に効く。** ひな形が「小規模で十分速いコードをこのために複雑にしない」と
禁じているものを、診断が名指しして依頼文へ入れる。

## 7. 戻す不変条件

この版は当初「見える入口はブック添付の1本だけ。用途選択、相談、簡易モードの入口を
戻さない」を持ち、`tests\test-shortest-path.js` が門番として次を検査している。

- `screens.count === 10`
- `setMode` / `modeScreen` / `isSimple` / `startSimple` が無い
- `nextIndex({}, bookScreen) === diagnoseScreen`
- 製品コードに「簡易モードで始める」「AIで相談する」が無い

**この門番を書き換える。** 消すのではなく、新しい不変条件へ差し替える。

| 旧 | 新 |
|---|---|
| 画面は10 | 画面は11 |
| ブックの次は必ず診断 | 入口の次は必ずブック |
| モード API を持たない | 入口はちょうど3つ。増やす API を公開しない |
| 「簡易モードで始める」「AIで相談する」が無い | 同じ。β1.10 の言い回しは戻さない |
| — | 3つの入口が**別々の診断ひな形と改修ひな形**を持つことを検査する |

最後の1行が要点である。β1.10 の3入口が戻っていないことは、**入口の数ではなく
中身**で検査する。β1.10 の3つは同じ作業への3つの言い方で、どれを選んでも
同じひな形へ着いた。ここでの3つは違う作業で、着く先が違う。ひな形フォルダが
分かれていることが、その差の機械的な証拠になる。
