# MacroStudio β2.00 設計 — 導線を一本化する

2026-08-05。先生の判断で確定した設計。

**版は β2.00 のままである。** 正式 v2.00 へは上げない。本書は
[README.md](README.md) が挙げる β2.00 の設計文書の 6 冊目で、
[DESIGN-ENTRANCES.md](DESIGN-ENTRANCES.md)（5 冊目）で入れた 3 入口を撤回し、
導線を 1 本へ戻した回の記録である。

**実装済み。** 本文の契約は `docs/SPEC.md` §2・§5・§9・§11 へ取り込んだ。
そちらが正本で、本書は経緯の記録である。

---

## 1. なぜ戻すのか

§1 の当初の判断はこうだった。

> **何をするかは、マクロを見てから決める。**
> 分岐は無くなるのではなく、**分岐の位置が「最初」から「診断の後」へ動く**。

DESIGN-ENTRANCES はこの骨格の上に、別の問題を解こうとして 3 入口を足した。

> 初心者がただマクロを動くようにしたいだけなのに、高速化やエラー処理が
> ブロッカー扱いされてたらうっとおしい。

問題そのものは実在する。しかし置いた場所が悪かった。**用途を選ばせる画面を
ブックの前に置いた時点で、分岐は「最初」へ戻っている。** 名前が
「AIで改修 / AIで相談 / 簡易モード」から「マクロ改修 / リファクタ / フリー依頼」へ
変わっても、読者がしていることは同じである — **まだ何も見ていない段階で、
自分のマクロに何が起きているか分からないまま、道を 1 つ選ばされている。**

β1.10 の 3 択を消した理由がそのまま当てはまる。だから戻す。

## 2. 元の問題は、別の場所で解く

「動かしたいだけの人に、速さや書き方の話をブロッカーとして見せない」は
捨てない。解く場所を 2 つに分ける。

| 元の入口 | どこへ行ったか |
|---|---|
| マクロ改修 | **一本道そのもの。** 診断は「動くか」だけを問う（`01_診断/` は 1 つ） |
| リファクタ | **変更範囲**（§4）。用途ではなく「どこまで変えてよいか」である |
| フリー依頼 | **操作の 1 つ**（`02_改修/06_自分で改修内容を書く.md`）と、画面 4 の記入欄 |

診断が「動くか」だけを問うのは変わらない。だから「セル逐次ループが遅い」は
今も原理的に出てこない。それは入口が分かれていたからではなく、**診断ひな形が
1 つで、その 1 つがそう書いてあるから**である。入口は要らなかった。

## 3. 推奨操作は、少数の見出しに束ねる

画面 3 の操作カードを、ひな形が名乗る `## 分類` ごとに束ねる。

| 見出し | 中身 |
|---|---|
| 環境依存・外部実行の見直し | Win32 API の互換化・代替／Shell・外部プロセス呼び出しの置換・安全化 |
| 実行環境・参照先の移行 | ハードコードされたパスの置換／新旧環境間の参照先変更 |
| その他の改修 | 診断で見つかった故障を直す／自分で改修内容を書く |

**束ねるのは表示だけである。** 同じ見出しの下の 2 つは別ファイルのままで、
別々に選べ、選んだものだけがそれぞれ `【ひな形名】` 付きで改修依頼へ入り、
run manifest にも別項目として残る。1 つの指示に混ぜない。混ぜれば、Shell の
置換を頼んでいないのに Shell の話が依頼へ入る。

上位 2 つは先生の指定そのままである。3 つ目を足したのは、A/B のどちらにも
属さない受け皿（診断で見つかった故障／自分で書く）を落とさないためで、
**B（要改修）に入った指摘は必ずどれかのひな形が受け持てなければならない**
という DESIGN-ENTRANCES §5 の不変条件を切らない。

見出しの一覧をアプリは持たない。`## 分類` の文字列で束ねるだけである
（`tests\test-shortest-path.js` が、分類名が製品コードに書かれていないことを検査する）。

## 4. リファクタは「変更範囲」になる

用途ではない。**どこまで変えてよいか**である。画面 3 の下段で選ぶ。

| 選択肢 | `## 構造変更` | 既定 |
|---|---|---|
| 必要最小限の変更 | `禁止` | ● |
| 大規模な構造変更・リファクタリングを許可する | `許可` | |

`VBAリファクター` の 12 の判断基準とその抑制規則は捨てず、後者の
`## 改修指示` へそのまま移した。`tests\test-preset-migration.js` が全項目を
検査しているので、移動で文言が痩せていたら落ちる。

**どちらの名前も「許すこと」で書く。** 「〜しない」を外させる形の選択肢を
置かない。読者に二重否定を読ませないためである。

### 4.1 OFF のときは、文言だけでなく機械で止める

依頼文へ「構成を変えないでください」と書くのは必要だが十分ではない。
返答が守らなければ、書いたことは何の保証にもならない。だから取り込みが
**4 つを機械的に検査する**（SPEC §5.4.2）。

1. 読み込んだブックに無いモジュールが返ってきた（分割・クラス化の実体）
2. 既存モジュールから `Sub` / `Function` / `Property` の宣言が消えた
3. 別のモジュールにあった手続きが移ってきた
4. 元が 40 行以上のモジュールで、変更行数が元の 80% 以上

1 つでも当たれば**返答全体を拒否**する。一部だけ適用した状態は作らない。
拒否の文は、増えたモジュール名・消えた手続き名・移動元・行数を名指しする。

**手続きとして数えないもの**が 2 つある。どちらも実装しながら分かったことである。

- **`Declare` 文**。VBA の文法上は `Function` だが、これを取り除くことは
  Win32 API 改修そのものである。数えると、この製品が最もよく行う改修が
  既定設定で通らなくなる。
- **そのモジュールが元から持っていた名前**。VBA は `Test` や `Main` を複数の
  モジュールに私的に持てる。名前だけで突き合わせた最初の実装は、実 GUI で
  `testdata/test_large.xlsm` を読んだ 1 回目に、動いていない手続きを
  「移動した」と誤検知した。単体テストでは出ず、実ブックを実 GUI に通して
  初めて出た。回帰テストを node 側に足してある。

**検査 1 の例外は、操作自身が名乗る。** 改修ひな形が `## 認める構造変更` に
`- モジュール追加` と書いていれば、その操作を選んでいるあいだ追加を通す。
Win32 API の代替関数を新しい標準モジュールへまとめる改修は、その操作自体が
要求している構造変更であって、黙って混ぜ込まれたものではない。同梱では
Win32・OS依存・保存先の 3 つが名乗り、残りは名乗らない。
**どの操作が名乗るかをアプリは知らない。**

### 4.2 検出できないものを、検出したとは言わない

上の 4 つ以外の構造変更（手続きの中身の作り替え、変数の整理、コメントの
書き直し）は検出できない。同名のまま中身を全部書き換えた返答は、4 つの検査を
すべて通る。**画面はそれを同じ場所に書く。**

これは弱点の告白ではなく、契約の一部である。「必要最小限の変更」に
チェックが入っていることが「構造は変わっていません」の保証だと読まれると、
読者は差分を読まなくなる。テストが `tests\test-change-scope.js` で
「同名のまま中身を書き換えた返答は通ること」を明示的に固定しているのは、
その日が来たときに誰かが「検査しているはずだ」と言えないようにするためである。

## 5. 画面

11 → 10。入口の画面が消え、全体が 1 つ繰り上がる。

```
0  book        ブックを読み込む
1  diagnose    診断の受け渡し
2  result      診断結果 A〜D
3  nextStep    推奨操作（分類ごと）＋ 変更範囲
4  repairInput 改修する内容
5  repair      改修の受け渡し
6  review      差分
7  output      出力名
8  build       ビルド
9  done        完了
```

分岐は 3 → 1。残るのは「置換のみの経路は diff へ直行」だけで、これは
読者に見えない実装上の合流である。

## 6. 門番の差し替え

DESIGN-ENTRANCES §7 が `tests\test-shortest-path.js` に置いた不変条件を、
もう一度差し替える。**消すのではなく、いまの答えを固定する。**

| 3 入口版 | 一本道版 |
|---|---|
| 画面は 11 | 画面は 10 |
| 入口の次は必ずブック | **ブックの次は必ず診断**（`nextIndex({}, book) === diagnose`） |
| 入口はちょうど 3 つ | **入口 API が無い**（`entranceScreen` / `setEntrance` / `isDiagnosisSkipped`） |
| β1.10 の言い回しは戻さない | 同じ。加えて「何をするか選びます」も戻さない |
| 3 入口が別々のひな形を持つ | **改修ひな形が `## 分類` を名乗り、分類が 2 つ以上ある** |
| — | **分類名と変更範囲名が製品コードに書かれていない** |
| — | 変更範囲の既定が `構造変更: 禁止` である |

最後から 2 番目が要点である。束ねることと決め打ちすることの違いは、
**アプリがその文字列を持っているかどうか**でしか機械的に見分けられない。

## 7. やらないこと

- **入口を戻さない。** 用途を先に名乗らせる画面は、名前が何であれ置かない
- **診断を飛ばす経路を作らない。** 「診断する / しない」はトップレベルの分岐である
- **リファクタを用途に戻さない。** 変更範囲の詳細オプションのままにする
- **検出できないものを検出したと表示しない**（§4.2）
- **v2.10 の高機能モードを先行実装しない。** 入口も部分実装も隠しフラグも置かない
  （将来スコープは SPEC §11.1 に保存した）
- **版名を上げない。** 作業中も成果物も UI も文書も β2.00 のままである
