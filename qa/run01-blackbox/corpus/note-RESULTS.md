## 何を根拠にしているか

判定は2本立て:

1. **run フォルダの実在** — 画面1へ到達すると `exports\<stem>_<時刻>\run-manifest.json` が書かれる。
   これは製品が「実際に読んだモジュール一覧」で、スクリーンショットより強い証拠。
   本セッションで **37 個の run フォルダ**が新規に作られた（`exports` を時刻で絞って実測）。
2. **拒否されるべき本は run フォルダが出ないこと**＋**実画面の拒否コード**。

## 途中で 1 度止まった（関門が働いた）

`G09` の拒否直後、`F06` `B02` が連続で `could not open the file dialog` になり、
**2連続失敗の停止条件でバッチを止めて画面を撮った**（`shots\N_INJ_STOP_B02`）。

原因は**私の座標の誤り**で、製品側の問題ではなかった:
拒否バナーが出ると ［選び直す］は `y=397` から **`y=546`** へ下がる（desktop の「約180px下」ではなく約150px）。
候補座標を実測どおりに直したところ、同じ6本が一度で全て通った。

**これは HANDOFF-3 §0 が要求した関門がそのとおり働いた記録である。**
前任は同じ状況で30冊クリックし続けた。止めて撮ったので、原因が1回で分かった。

## 拒否時の画面についての観察（台帳へ追記済み）

拒否バナー（E-ATTACH-02）が出ても、**直前に読み込んでいた本のカードはそのまま残る**。
`shots\N_INJ_STOP_B02` では G09 の拒否バナーの下に G03 のカードがあり、
**［次へ］は有効のまま**だった。つまり「拒否された本は読み込まれず、前の本が生きている」。
状態としては筋が通っているが、利用者から見ると
「赤い枠が出ているのに次へ進める」画面なので、意図した設計か確認の価値がある。

  `exports\` の run フォルダか JSON を数えること**。
